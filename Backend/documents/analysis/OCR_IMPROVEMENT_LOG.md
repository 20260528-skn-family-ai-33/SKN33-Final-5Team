# 영수증 이미지 → CSV 정리 개선 기록

기록 시작: 2026-11-02. 영수증 사진(`영수증.png`, GS25, 567×1140, 72dpi)을 올려 "엑셀로 정리해줘"를 요청했을 때 발견한 오류와 수정 내역이다. 각 항목은 **증상 → 원인 → 수정(코드) → 검증** 순서로 적는다. 수치는 위 영수증 1장 기준이며 일반 정확도를 뜻하지 않는다.

## 처리 흐름 (이미지 입력)

```
업로드 → [파서] EXIF 회전 보정 → 레이아웃 분석(PP-DocLayout_plus-L)
       → 영역별 라우팅: text → PaddleOCR(PP-OCRv5 mobile det + korean rec) / table → Docling / 그 외 → 검토 필요
       → [설계] 문서 표 정리 고정 흐름(document_rows_template): 항목 질문 → read_document → extract_information(rows) → export_result(csv)
       → [실행] LLM이 OCR 텍스트에서 항목별 값 추출, 원문 인용과 대조해 검증 → CSV 저장
```

파서 모델은 모두 CPU에서 실행된다(`A4B_PADDLE_DEVICE` 기본값 `cpu`).

## 1. "전체 다"가 열 이름 하나로 저장됨

| 구분 | 내용 |
|---|---|
| 증상 | CSV 열이 `file_name, row, 전체 다, status, evidence` 하나뿐이고, OCR 줄이 한 행씩 나열됨 |
| 원인 | 항목 질문("어떤 항목을 한 줄씩 뽑을까요?")의 답을 쉼표로 나눠 그대로 열 이름으로 사용. "전체 다"처럼 '전부'를 뜻하는 답을 구분하지 않음 (모델 문제가 아니라 코드로 고정된 흐름) |
| 수정 | `Backend/agent_builder/design/document_rows_template.py` — `wants_all_fields()` 추가. "전체 다/전부/모두/알아서/다 뽑아줘" 등을 인식해 영수증 요청이면 기본 항목(상품명, 단가, 수량, 금액)으로 구성하고 안내, 그 외 문서는 항목 이름을 다시 질문. 명령형("다 뽑아줘")이 취소로 오인되지 않도록 취소 판별보다 먼저 확인 |
| 검증 | 테스트 16개 추가, `tests/design`·`tests/conditions` 507개 통과. 같은 대화를 재현해 4개 열 생성 확인 |
| 위치 | 브랜치 `fix/document-rows-all-fields`, 커밋 `61ebbcb` |

## 2. 작은 사진에서 상품 영역 OCR이 깨짐

| 구분 | 내용 |
|---|---|
| 증상 | 상품 3줄 대신 `vmv, 1, 1, 420` 한 줄만 추출됨. 상품 영역 OCR 결과가 `1-3 / vmv / 1 / J / 권 / 으록 / 인 / -420`, 인식 점수 0.00~0.61 (다른 영역은 0.95 이상) |
| 원인 | 라우터는 정상. 레이아웃이 자른 상품 영역(383×122px)을 원본 크기 그대로 OCR에 넘겨 글자 줄 높이가 약 15px. 검출 모델이 줄을 합쳐 버림 |
| 확인 방법 | 같은 crop을 원본 / 여백 추가 / 2배 확대 / 2배+여백으로 각각 OCR → 2배 확대만으로 상품 3줄 인식 |
| 수정 | `Backend/documents/analysis/pipeline.py` — `ocr_scale()` 추가. 원본 긴 변이 1500px 미만이면 텍스트 영역 crop을 정수배(최대 3배, LANCZOS) 확대 후 OCR. 표 영역은 Docling용으로 원본 유지. 배율은 `crop_scale`로 기록(좌표 복원용), 기준은 `policy.ocr_upscale_below/ocr_max_scale`에 남김 |
| 검증 | 상품 영역 최저 점수 0.00 → 0.80, `마늘빅프랑크 1 2,100 / 예거라를러레몬 3,380 / 마운틴들러스트 2,100` 인식. 테스트 2개 추가 |
| 위치 | 브랜치 `feat/parser-ocr-improvement` (`fix/document-rows-all-fields`의 `16b7a86`과 같은 변경) |

## 3. 레이아웃 영역을 못 찾으면 이미지가 통째로 비어 버림

| 구분 | 내용 |
|---|---|
| 증상 | "교환/환불 안내" 문단이 결과에서 빠짐. 더 흐린 사진이면 상품 영역까지 빠질 위험 |
| 원인 | 레이아웃 점수 0.5 미만 영역은 버림(`detection_threshold=.5`). 이 영수증의 영역 점수는 0.507~0.544로 기준선에 붙어 있음. 영역이 하나도 남지 않거나 레이아웃 엔진이 실패해도 **이미지 전체를 읽는 대체 경로가 없었음** |
| 수정 | `pipeline.py` — 사용할 수 있는 text/table 영역이 하나도 없는 이미지는 이미지 전체를 (같은 기준으로 확대해) PaddleOCR로 한 번 읽음. 라우팅 규칙 `no_text_region_detected` 또는 `layout_unavailable`을 기록하고 검토 사유 `whole_image_ocr_fallback:*`를 남김. 보완 처리 상한(`max_supplements`) 안에서만 실행 |
| 검증 | 테스트 2개 추가(영역 점수 0.3 → 전체 OCR 1회 / 레이아웃 실패 → 전체 OCR). 문서 분석 테스트 24개 통과. 실제 영수증에서 모든 영역 점수를 0.3으로 낮춰 재현 → 전체 OCR로 66줄 인식 |
| 위치 | 브랜치 `feat/parser-ocr-improvement` |

### 참고: 영역별 OCR vs 이미지 전체 OCR (같은 영수증, 둘 다 2배 확대)

| 항목 | 영역별 OCR (기본 경로) | 이미지 전체 OCR (대체 경로) |
|---|---|---|
| 처리 시간 (CPU) | 69.2초 | 39.7초 |
| 교환/환불 안내 문단 | 없음 (영역 누락) | 읽음 |
| 주소 `경기 용인시 처인구` | 빠짐 | 읽음 |
| `합계수량/금액 … 7,500` | `한계수량/금액 … 7,580` | `합계수량/금액 … 7,500` |
| `판촉/팝 할인` | `판족/팝 할인` | `판촉/팝 할인` |
| `예거라들러레몬 3,300` | `3,380` | `3,380` |
| 상품별 수량 | 1번째 상품 수량만 순서대로 | 수량 숫자의 줄 순서가 섞임 |

영수증처럼 글자만 있는 단일 열 문서는 이미지 전체 OCR이 더 많이 읽고 더 빨랐다. 다만 줄 순서가 섞여 상품-수량 짝이 틀어질 수 있다. 영수증에서 어느 쪽을 기본 경로로 둘지는 여러 장으로 비교한 뒤 정한다(아래 남은 과제 1).

## 4. OCR 조각이 줄 단위가 아니라 검출 순서로 나열됨

| 구분 | 내용 |
|---|---|
| 증상 | 상품 영역 텍스트가 `마늘빅프랑크 \| 1 \| 2,100 \| 예거라를러레몬 \| 3,380 \| 마운틴들러스트 \| 2,100 \| 1 …`처럼 조각마다 한 줄. 2·3번째 상품의 수량이 다른 위치에 붙고, 카드 전표는 `9490-94… \| 카드번호`로 값이 이름보다 먼저 나옴 |
| 원인 | PaddleOCR은 조각별 좌표(`rec_boxes`, `[x0, y0, x1, y1]`)를 함께 반환하지만, 파이프라인은 `'\n'.join(rec_texts)`로 검출 순서대로 이어 붙여 위치 정보를 버림 |
| 수정 | `pipeline.py` — `ocr_text()` 추가. 조각을 세로 중심 순으로 정렬하고, 세로 구간이 짧은 쪽 높이의 절반 이상 겹치면 같은 줄로 묶어 가로 순서로 공백 연결. 줄의 기준 구간은 첫 조각으로 고정(넓히면 기울어진 사진에서 인접 줄이 연쇄로 합쳐짐). 좌표가 없거나 개수가 맞지 않으면 기존 방식 유지. 빈 조각 제외 |
| 검증 | 테스트 1개 추가(행 묶기, 살짝 걸친 조각 분리, 좌표 없음/불일치 시 기존 방식). 문서 분석 25개, 문서·워크플로우 엔진·설계 349개 통과 |
| 위치 | 브랜치 `feat/parser-ocr-improvement` |

실제 영수증 결과 (상품 영역):

| 경로 | 수정 전 | 수정 후 |
|---|---|---|
| 영역별 OCR | 조각 13줄, 수량 위치 섞임 | `마늘빅프랑크 1 2,100` / `예거라를러레몬 3,380` / `마운틴들러스트 1 2,100` / `한계수량/금액 3 7,580` / `판족/팝 할인 -420` |
| 이미지 전체 OCR | 조각 66줄 | `마늘빅프랑크 1 2,100` / `예거라를러레몬 1 3,380` / `마운틴틀러스트 3 2,100 2` / `합계수량/금액 7,500` / `판촉/팝 할인 -420` |

- 영역별 OCR에서 2번째 상품 수량이 없는 것은 OCR이 그 `1`을 검출하지 못한 것이다(정렬 문제 아님).
- 이미지 전체 OCR에서 `합계수량/금액`의 수량 `3`과 잡음 `2`가 3번째 상품 줄에 합쳐졌다. 사진이 기울어 행 간격이 좁아진 구간에서 절반 겹침 기준이 느슨한 것으로 보인다(남은 과제 6).

## 5. 숫자 오인식을 알아챌 방법이 없음

| 구분 | 내용 |
|---|---|
| 증상 | `3,300→3,380`, `7,500→7,580`처럼 틀린 금액이 `status=verified`로 CSV에 저장됨. 추출 검증은 "값이 OCR 원문에 있는가"만 보므로 OCR이 틀리면 그대로 통과 |
| 원인 | OCR이 같은 방식(0→8)으로 일관되게 틀려, 상품 금액 합(2,100+3,380+2,100=7,580)과 잘못 읽은 합계(7,580)가 서로 맞아 버림 |
| 수정 | `Backend/workflow_engine/executors/document/receipt_check.py` 추가, `extract_information.py` 행 추출 직후 호출. 모델 호출 없이 코드로 두 관계를 확인: ① 상품 금액 합 = 합계(`수량/금액`·`소계`·`총액` 줄) ② 합계 + 할인(`할인` 줄의 음수) = 결제 금액(`사용금액`·`결제금액`·`합계`·`신용카드` 줄, 여러 줄 중 하나만 맞으면 일치). 결과를 `합계_검산` 열(`일치` / `불일치: …` / `확인 불가 (…)`)로 `status` 앞에 기록. **값은 고치지 않음.** 금액 열(`금액`·`판매금액`·`가격` 등)이나 합계·결제 줄이 없으면 열을 만들지 않음. `카드번호`·`승인번호` 줄, 날짜·시각·마스킹 번호는 숫자로 보지 않음. `합계_검산`은 예약 열 이름에 추가 |
| 검증 | 테스트 14개 추가. 엔진·설계·문서 363개 통과. 테스트 영수증(영역별 OCR 결과)에서 `불일치: 영수증 합계 7,580 + 할인 -420 = 7,160 ≠ 결제 금액 7,080` — ①은 일관된 오인식으로 통과했지만 ②가 잡아냄. 계산 시간 영수증 1장당 약 0.14ms |
| 위치 | 브랜치 `feat/parser-ocr-improvement` |

## 6. RunPod 연결에서 영수증 요청이 첫 단계에서 멈춤 (최신 main)

| 구분 | 내용 |
|---|---|
| 증상 | 영수증을 올리고 "엑셀로 정리해줘"를 보내면 바로 `도구 지원 판단을 완료하지 못했습니다.` (오전의 이전 main에서는 정상) |
| 원인 | PR #21에서 Docker 기본값이 `A4B_CAPABILITY_MODE=enforce`로 바뀌어, 설계 전에 `OllamaPlanner`가 모델에 지원 여부를 묻는다. 이 호출은 `urllib` 기본 User-Agent(`Python-urllib/3.x`)로 나가는데 **RunPod 프록시가 403으로 차단**한다(`A4B/0.1`이면 200). 검증 클라이언트는 이미 `A4B/0.1`을 쓰고 있었고, 로컬 Ollama에는 차단이 없어 드러나지 않았다 |
| 수정 | `agent_builder/design/nodes/direct_conversation.py`(`OllamaPlanner`), `workflow_engine/unified_tools/model_operations.py`(모델 도구 호출)에 `User-Agent: A4B/0.1` 추가. 헤더 확인 테스트 추가 |
| 위치 | 브랜치 `feat/parser-ocr-improvement` |

## 7. 항목 답변을 조건 검사 모델이 필터로 오해해 저장 불가 (최신 main)

| 구분 | 내용 |
|---|---|
| 증상 | 항목 질문에 `상품명, 수량, 단가, 금액`으로 답하면 `조건 판정을 완료하지 못했습니다. 모델 연결과 출력 계약을 확인하세요.`, 저장 시 `필수 조건과 근거 검증을 완료한 뒤 저장할 수 있습니다.` |
| 원인 | PR #21에서 `A4B_CONDITION_MODE=enforce`도 기본값이 됨. 조건 검사기는 표 필터·중복 제거·예약만 다루고 그 밖의 업무는 `outside_scope`로 위임하도록 설계됐지만, 범위 판단 자체를 모델이 한다. 같은 대화를 3회 재현하자 3회 모두 항목 목록을 `filter`로 읽고 질문 9개(필터 연산자·값, 중복 기준, 예약, 출력 형식)를 만들었고, 실제 실행에서는 출력 규격 검사 2회 실패(`ConditionContractError`) |
| 수정 | `document_rows_template.document_rows_applies()` 추가 — 문서 표 정리 고정 흐름이 처리할 대화(요청 또는 항목 답변)인지 코드로 판단. `condition_check`는 이 경우 모델 호출 없이 `outside_scope: 문서 표 정리 고정 흐름으로 위임`으로 처리. 취소·변경 답변, 표 파일이 함께 있는 경우, 다른 요청은 기존대로 모델 검사 |
| 검증 | 조건 검사 enforce에서 요청·항목 답변의 조건 모델 호출 0회, 위임 범위 테스트 추가. 설계·엔진·지원 판단·조건·문서 689개 통과. 영수증 대화당 조건 판정 모델 호출(회당 약 7초) 제거 |
| 위치 | 브랜치 `feat/parser-ocr-improvement` |

## 샘플 이미지 전체 흐름 시험 (2026-11-02)

앱 API로 업로드 → "이 영수증을 엑셀로 정리해줘" → 항목 답변 → 저장 → 실행 파일 업로드 → 실행 → CSV까지 자동으로 진행했다. 샘플은 Wikimedia Commons에서 받았다(마트 영수증, 우체국 사진 2장, 1920년대 손글씨 한자 영수증). 실행 환경: Docker(CPU 파서) + RunPod Ollama `qwen3:8b-q4_K_M`.

| 샘플 | 워크플로우 | 실행 | 결과 |
|---|---|---|---|
| 동대문마트 영수증 (1920×2571) | ✅ `read_document → extract_information(상품명,수량,단가,금액) → export_result` | ✅ 5행 | 상품명 5/5, 단가 5/5, 금액 5/5, 수량 4/5(`1`을 `—`로 읽음). 셀 20개 중 19개 정확 |
| GS25 영수증 (567×1140, 저해상도) | ✅ 같은 구조 | ✅ 3행 | 2번째 상품 수량 누락, `3,300→3,380`, 이름 1자 오인식. **`합계_검산: 불일치 …7,160 ≠ 결제 금액 7,080`으로 오인식을 표시** |
| 우체국 창구 사진 | ❌ 설계 중단 | – | 파서 `partial`(64자) → `자료 <ID>의 변환 상태를 확인해야 합니다.` 문서가 아니므로 막는 것은 맞지만 안내 문구에 파일명·이유가 없음 |
| 손글씨 한자 영수증 | ❌ 설계 중단 | – | 파서 `partial`(68자) → 위와 같음 |

- 마트 영수증은 큰 글씨 라벨이 `합 계 → 게`, `현 금 → 회`로 읽혀 검산 열이 생기지 않았다. 라벨을 못 읽어도 상품 금액 합(11,400)과 정확히 같은 금액만 있는 줄이 있으면 `일치 (합계 라벨 미인식, 11,400 줄 확인)`으로 표시하도록 보완했다. 불일치는 라벨이 있을 때만 판단한다.
- 단계별 시간(마트 / GS25): 업로드·파싱 95.6초 / 61.8초, 요청 7.4 / 6.4초, 항목 답변 8.3 / 5.6초, 저장 2.8초, 실행 파일 업로드·파싱 48.9 / 62.8초, 실행(LLM 추출) 24.9 / 14.2초. **영수증 1장에 약 3분이며 같은 파일을 설계 때와 실행 때 두 번 파싱한다**(남은 과제 9).

## 처리 시간 영향

같은 영수증, 같은 컨테이너에서 확대를 끈 경우(= main 동작)와 켠 경우를 각각 워밍업 1회 후 3회 측정했다. 측정 PC는 RAM 7.7GB에 여유 메모리가 1GB 미만이라 편차가 크다(같은 설정에서 27~47초).

| 단계 | 확대 끔 (중앙값) | 확대 켬 (중앙값) | 차이 |
|---|---|---|---|
| 레이아웃 분석 | 12.1초 (11.4~16.6) | 15.4초 (13.1~19.9) | 확대와 무관한 단계 → 측정 편차 |
| OCR | 15.0초 (15.0~29.9) | 18.1초 (14.5~18.8) | **약 +3초 (약 +20%)** |
| 전체 파서 | 27.6초 (27.1~47.2) | 35.3초 (28.5~39.3) | 편차 범위 안 |
| 줄 단위 정렬 `ocr_text()` | – | 0.1ms / 영수증 | 무시 가능 |
| 합계 검산 `receipt_check.check()` | – | 0.14ms / 영수증 | 무시 가능 |
| 전체 OCR 대체 경로 | – | 영역을 못 찾을 때만 실행 | 평소 0 |

- 확대는 OCR 입력 픽셀을 4배로 늘려 OCR 단계를 약 3초 늘린다. 상품 줄 인식(점수 0.00→0.80)과 비교하면 감수할 만하다고 판단.
- 실행 시간의 대부분은 요청마다 Paddle 프로세스를 새로 띄워 모델을 불러오는 데 쓰인다. 모델 상주(워커 재사용)가 확대로 늘어난 시간보다 더 크게 줄일 수 있는 지점이다(남은 과제 8).

## 남은 과제

1. **영수증 여러 장으로 경로 비교** — 영역별 OCR vs 이미지 전체 OCR의 금액 정확도·누락 줄·시간을 같은 평가 세트로 측정해 기본 경로 결정.
2. **일부 영역만 누락되는 경우** — 다른 영역이 있으면 대체 경로가 동작하지 않아 0.5 미만 문단(교환/환불 안내)은 여전히 빠진다. 낮은 점수 영역을 겹침 검사 후 추가 OCR하거나, 덮지 못한 면적이 크면 전체 OCR과 비교하는 방안 검토.
3. **숫자 오인식** — `3,300→3,380`, `7,500→7,580` 등. 원본 해상도 한계. 더 큰 OCR 모델(`PP-OCRv5_server`) 또는 영수증 데이터로 인식 모델 파인튜닝 검토.
4. **머리글·합계 항목** — 현재 흐름은 "한 줄에 상품 하나"라서 가맹점명·결제일시·합계·결제수단은 기본 항목에 없음.
5. **CSV 가독성** — `evidence` 열에 긴 JSON이 들어가 엑셀에서 보기 어려움.
6. **기울어진 사진의 줄 묶기** — 이미지 전체 OCR에서 인접 줄이 합쳐지는 경우가 있음. 조각 기울기 보정(`rec_polys` 사용)이나 겹침 기준 조정을 평가 세트로 검토.
7. **합계 검산 라벨 확장** — OCR이 라벨을 깨뜨리면(`-합신 계드 7,080`, `용 카 7,088`) 결제 줄로 인식하지 못함. 여러 영수증에서 깨지는 형태를 모아 라벨 규칙을 보강.
8. **파서 모델 상주** — 요청마다 레이아웃·OCR 모델을 새 프로세스로 불러옴. 워커를 재사용하면 영수증 1장 처리 시간을 크게 줄일 수 있음(측정 필요).
9. **같은 파일 중복 파싱** — 설계 업로드와 실행 업로드에서 같은 이미지를 각각 파싱(영수증 1장 50~60초씩). 파서 결과의 `document_id`가 원본 SHA-256이므로 해시 기준 재사용 검토.
10. **문서가 아닌 이미지 안내** — `자료 <UUID>의 변환 상태를 확인해야 합니다.` 대신 파일명과 이유(글자를 거의 찾지 못함 등)를 안내.

## 검증 방법

- 단위 테스트: 문서 분석 테스트는 `unittest` 기반이며 Pillow가 있는 `.venv-document-analysis`에서 실행한다(`.venv-agent`에는 Pillow가 없어 pytest로 수집되지 않음).
  ```bash
  docker run --rm --entrypoint sh -v "<repo>/Backend:/src:ro" a4b-agent-studio:local \
    -c "cp -r /src /tmp/b && cd /tmp/b && /app/Backend/.venv-document-analysis/bin/python -m unittest discover -s tests/documents/analysis -t ."
  ```
- 실제 영수증 재분석: 컨테이너 안에서 `documents.analysis.pipeline.run(이미지, 작업폴더)`을 호출하고 `document_analysis.blocks` 중 `engine == 'paddleocr'` 블록의 `text`, `data.ocr_scores`, `data.crop_scale`을 비교한다. 대체 경로 재현은 `LocalEngines.run`을 감싸 layout 결과의 `score`를 0.3으로 낮춰서 한다.
- 실행 기록 확인: 앱 데이터의 `document-results/<문서 해시>/<실행 ID>/`에 `result.json`(영역·OCR 블록·라우팅 결정), `crop-region-*.png`(잘린 영역), `attempt-*/engine.log`가 남는다.
