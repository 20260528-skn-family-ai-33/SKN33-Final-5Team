# SKN33-Final-5Team · A4B — 대화로 만드는 워크플로우·에이전트

**노드 라이브러리 통합판 v2.3 · 2026-10-13**

업무 상황·필요한 결과·자료를 입력하면 Deep Agents가 전체 생성 대화를 총괄하여 부족한 조건을 직접 질문하고, 답변을 반영해 등록된 노드의 설정·입출력 연결을 구성·수정합니다. 별도 질문 모델이 먼저 판단하는 경로는 제거했습니다. 확인한 구성을 저장하면 LangGraph가 실제 업무를 실행합니다. 역할과 처리 규칙을 버전으로 저장하는 노드 라이브러리, 예약형 표 처리, 정책 기반 응대 검수·사람 승인을 지원합니다.

화면은 **노드 만들기 → 워크플로우 설계 → 서비스 실행**으로 구성합니다. 팀원이 제공한 `Demo`에서 노드 라이브러리와 화면·캔버스 개선을 선별 통합했습니다. 기존 A4B 검수·승인·예약·복구 기능과 기본 모델 설정을 유지합니다.

## 설치와 실행

Node.js 24, Python 3.12 권장(3.11~3.14 사용 가능). 최초 패키지 설치에는 인터넷이 필요합니다. **macOS와 Windows 모두 같은 명령**을 저장소 최상위 폴더에서 실행합니다. macOS는 터미널, Windows는 PowerShell 또는 VSCode 터미널을 사용합니다.

```bash
npm --prefix Frontend ci
npm --prefix Frontend run setup
npm --prefix Frontend run dev
```

접속: **http://127.0.0.1:3030/**. 서버 터미널을 유지하고, 종료는 Ctrl+C입니다.

- `run setup`은 설치된 Python 3.12 → 3.13 → 3.11 → 3.14 순서로 찾아 `Backend/.venv-agent`를 만들고 `Backend/requirements-agent-lock.txt`를 설치합니다. Windows는 `py` 런처, macOS는 `python3.12` 같은 명령을 찾습니다. 다른 Python을 쓰려면 `A4B_SETUP_PYTHON`에 실행 파일 경로를 지정하세요. Windows에 필요한 `tzdata`(예약 시간대)는 잠금 파일에서 Windows에만 설치됩니다.
- 더블클릭 실행: macOS `Frontend/scripts/실행.command`, Windows `Frontend/scripts/실행.cmd`. 같은 동작을 `npm --prefix Frontend run demo`로도 할 수 있습니다. 이미 실행 중이면 브라우저만 열고, 아니면 빠진 설치를 마친 뒤 빌드하고 서버를 시작합니다.
- 기존 macOS 명령(`./Backend/scripts/setup-agent-demo.sh`, `./Frontend/scripts/start-agent-demo.sh`)도 그대로 동작합니다.
- 서버는 `Backend/.venv-agent`의 Python을 자동으로 찾습니다(Windows `Scripts/python.exe`, macOS `bin/python`). 다른 환경은 `A4B_AGENT_PYTHON`에 절대 경로를 지정하세요.

선택 설정은 `Frontend/.env.example`을 `Frontend/.env`로 복사해 사용합니다. `npm run dev`와 `npm start`가 이 파일을 읽으며, 실제 모델 계정은 화면의 **모델 연결**에서 등록합니다.

### 모델과 문서

생성 대화·문서 답변·응대 검수는 화면의 **모델 연결**에서 계정을 연결해야 실제 모델 API를 사용합니다. 키를 생성 대화에 입력하지 마세요. 단순 표 읽기·필터·합계·파일 저장·예약 시간 계산은 모델을 호출하지 않습니다.

PDF 처리에는 별도로 `npm --prefix Frontend run setup:docling`으로 Docling을 설치합니다(macOS는 `./Backend/scripts/setup-document-demo.sh`도 가능). 예약 CSV 시연에는 필요하지 않습니다. 스캔 PDF OCR는 현재 범위 밖입니다.

## 노드 만들기와 재사용

1. **노드 만들기**에서 기본 노드 5개 또는 등록 도구 16종을 확인합니다.
2. 에이전트 노드는 이름·목적·지시사항·참고 텍스트를 저장합니다. 모델을 비우면 워크플로우의 모델을 사용하며, 특정 모델은 사용자가 명시적으로 지정합니다. 처리 노드는 문서·표 읽기, 숫자 필터, 건수·합계 집계를 저장합니다.
3. **워크플로우에서 사용**으로 설계를 시작하거나, 설계 화면에서 사용할 노드를 최대 10개 선택합니다. 직접 선택한 노드는 설계에 반드시 포함돼야 합니다.
4. 설계 챗봇이 생성한 연결을 캔버스에서 확인합니다. 확대·축소·화면 맞춤을 지원하고, 노드를 클릭하면 입력·출력·지시사항·고정한 버전을 확인할 수 있습니다.
5. 구성을 확인해 저장하고 **서비스 실행**에서 요청·자료를 입력합니다. 저장한 노드를 수정하면 새 버전이 생기며, 기존 흐름과 이미 선택한 이전 버전은 그대로 유지됩니다.

캔버스는 생성된 흐름과 설정을 확인하는 화면입니다. 직접 드래그해 노드를 이동하거나 연결선을 편집하는 기능은 이번 통합에 포함하지 않았습니다. 흐름 수정은 설계 챗봇으로 요청합니다.

새 `agent_node`는 요청·앞 단계 출력·연결 자료를 제한된 조회 도구로 읽고 답변을 작성합니다. 조회하지 않은 답변은 실패 처리하고, 입력은 45,000자, 출력은 12,000자 이내로 제한합니다. 검수 결과 1건을 명시적으로 연결해 수정문을 작성하면 기존 사람 승인 후보에 반영합니다. 노드 생성 자체는 모델 API를 호출하지 않으며, 설계·에이전트 실행에는 모델 연결이 필요합니다.

## 시연 1: 예약 재고 보고서

1. **워크플로우 설계 → 자료 연결**에서 `docs/examples/scheduled-workflow/inventory.csv`를 연결합니다.
2. “매일 오전 9시에 재고가 기준 수량보다 적은 상품을 찾아 보고서로 저장해줘.”라고 설명합니다.
3. 질문에 답합니다. 예: “Asia/Seoul, current_stock < threshold, 빈 값 제외·숫자 오류 실패·중복 유지, 원래 열의 CSV를 A4B 서버 보고서 보관함에 저장해주세요.”
4. 노드·연결·처리 규칙·예약을 확인하고 **자동화 저장**합니다. 저장 직후 예약은 중지 상태입니다.
5. **지금 실행**으로 결과·서버 보고서·처리 단계 로그를 확인합니다.
6. **15초 후 시험 예약**으로 실제 서버 타이머를 시험합니다. 대기 중에는 **예약 대기·관리 상태 → 시험 예약 취소**가 가능합니다.
7. **파일 갱신**으로 새 CSV를 등록하면 다음 실행에 반영됩니다. PC 원본 파일의 변경을 자동 감시하는 기능은 아닙니다.
8. 계속 실행할 경우 **예약 켜기**, 중지할 경우 **예약 중지**를 사용합니다.

`inventory-updated.csv`, `inventory-invalid.csv`, `inventory-none.csv`로 변경 반영·숫자 오류·부족 상품이 없는 경우를 시험할 수 있습니다.

## 시연 2: 합계·건수

`docs/examples/scheduled-workflow/team-sales.csv`를 연결한 뒤:

> 매주 월요일 오전 10시 Asia/Seoul에 amount를 team별로 합계 집계해 CSV를 A4B 서버 보고서 보관함에 저장해주세요. 빈 금액·비숫자는 실패로 처리하고 중복 행은 모두 포함해주세요. 정렬·요약은 필요 없습니다.

그룹별 합계는 A=0.3, B=200입니다. `aggregate_table`은 aggregation=count/sum, sum_field, 그룹 fields를 사용합니다. fields=[]이면 전체 집계입니다. 신청서 상태별 건수는 `applications.csv`로 시험할 수 있습니다.

## 시연 3: 응대 검수·승인

1. 시작 예시 **고객 응대 초안 검수**를 선택하거나 검수가 필요한 상황을 설명합니다.
2. 정책 자료를 연결하고 고객 문의·초안은 실행 시 입력한다고 정합니다. 예제는 `docs/examples/reply-review/`에 있습니다.
3. 워크플로우를 저장하고 문의·초안을 입력해 실행합니다.
4. 보고서에서 문제 유형·심각도·문제 구절·정책/고객 원문·수정안을 확인합니다.
5. 운영자가 문장을 편집하고 **수정 후 승인·저장**하거나 **거절**합니다.
6. **승인된 응대 CSV**에는 승인한 문장만 포함됩니다. AI 실행 성공과 운영자 승인 완료는 별도 상태입니다.

표와 정책 문서가 함께 연결된 예약 검수도 지원합니다. 정책이 없다면 없다고 표시하며 임의로 추정하지 않습니다. 검수 뒤에 조건 분기·수정·보고서 정리를 연결할 수 있습니다. `검수 → 답변 작성`에서 생성한 최신 수정문이 승인 입력란과 검수 보고서 표에 반영됩니다. 최초 검수 의견은 별도로 보존하며, 승인 CSV에는 운영자가 실제 승인한 문장만 포함됩니다.

답변 작성 노드의 검수 입력에는 보고서 **1건**만 연결합니다. 여러 고객의 검수 결과를 한 문장으로 덮어쓰는 연결은 오류로 처리합니다. 표 검수의 여러 보고서는 조건 분기·보고서 정리·개별 사람 승인으로 처리할 수 있습니다. 승인 후보 응대문은 12,000자까지 지원합니다.

검수 보고서는 승인 전 후보임을 표시하며 최종 응대는 사람 승인 화면에서 내보냅니다. 검수가 포함된 저장 흐름을 재사용해도 같은 승인 규칙을 적용합니다. 검수 흐름에서 `export_result`로 자동 내보내는 연결은 저장·실행 시 차단하고, `review_summary → write_result`의 승인 대기 진단 보고서는 저장할 수 있습니다. 보고서 표를 필터·정렬·집계하거나 재사용한 뒤 저장하는 연결도 유지합니다. 외부 발송은 하지 않습니다.

## 이번 코드 리뷰에서 수정한 네 항목 — v2.2.1

| 문제 | 수정한 동작 |
|---|---|
| 저장된 흐름을 재사용하면 검수·승인 기록이 사라짐 | 선택한 출력 포트와 무관하게 검수 기록·최신 수정 후보를 유지. 중첩 재사용도 승인 전 응대 내보내기 차단 |
| 검수 이후 작성한 수정문이 승인 화면에 반영되지 않음 | 최신 수정문을 승인 입력란·보고서 표의 후보 문장으로 연결. 원래 검수 보고서는 보존 |
| 조건·완료 노드가 같은 검수 보고서를 중복 표시 | 보고서 ID별로 한 번만 표시. 오래된 결과가 뒤에 전달돼도 최신 수정 후보 유지 |
| 문서 합계 45,000자 초과 시 답변 작성 오류 | 관련 문서 검색 호출을 복구. 검색 근거가 없으면 확인된 근거가 없다는 안내 반환 |

기존 저장 설정·체크포인트를 재시도할 때도 승인 전 자동 내보내기를 검사합니다. 승인·거절·중복 승인·CSV 저장은 기존 결정 기록을 사용합니다. 재사용한 동일 흐름을 여러 번 호출하면 실행 인스턴스별로 검수 항목을 구분합니다.

## 이전 리뷰에서 수정한 다섯 항목

| 문제 | 수정한 동작 |
|---|---|
| 저장 실패인데 버전·예약은 남음 | 설정·예약·소스를 한 트랜잭션으로 저장. 실패하면 모두 롤백. 기존 불완전 저장의 멱등 재호출도 초기화 복구 |
| 정책 문서를 연결하면 소스 초기화/갱신 실패 | 새 표를 검증할 때 기존 정책 문서와 문서 ID 유지 |
| 프로세스 종료 후 running 고정 | 부모 서버가 timeout/종료를 실패로 기록. 서버 시작 및 5초 검사에서 죽은 작업자·만료된 실행을 복구 |
| 15분 실행 / 5분 작업 점유 불일치 | 20초 heartbeat로 실행·예약 점유 갱신. 즉시 실행할 작업 하나만 claim. 오래된 소유자는 실행 완료·보고서 쓰기 차단 |
| 재시도 성공 뒤 예약 기록은 실패 | 실행·예약 결과 동기화. 최초 실패를 삭제하지 않고 attempts/attempt_history로 보존하고 화면에 재시도 이력 표시 |

실행 worker의 전체 제한은 기본 15분입니다. 생성 대화는 기본 3분입니다. 실행 소유권은 90초이며 살아 있는 부모 서버가 20초마다 갱신합니다. 부모가 사라져도 자식이 남아 있으면 점유 만료 후 실패로 복구되므로 잠시 지연될 수 있습니다. 실패 기록에서 같은 실행 ID·설정·체크포인트로 재시도합니다. 실패한 검수 노드 내부의 일부 모델 호출은 재시도 시 반복될 수 있습니다.

예약은 이 서버가 켜져 있을 때 실행합니다. **PC/서버를 끄면 예약도 멈춥니다.** 클라우드 배포·다중 사용자 인증·권한은 별도 구현 범위입니다. heartbeat·소유권 회귀 검사 통과는 실제 다중 서버 부하 검증을 완료했다는 의미는 아닙니다.

## 데이터와 전처리

운영 데이터는 저장소 최상위의 `data/`에 저장합니다. 실행 위치와 무관하게 같은 폴더를 사용하며, `EASYFLOW_DATA_DIR`로 변경할 수 있습니다. 상대 경로 설정도 저장소 최상위를 기준으로 해석합니다. 기존 DB·계정 보호 키·원본 업로드는 이동하지 않았습니다. ZIP은 API 키·계정 보호 키·DB·원본 업로드를 포함하지 않으므로 새 설치에서는 계정을 연결하고 예제로 시작합니다.

Git에는 환경 파일·개인 DB·원본 업로드·로그·ZIP·설치 환경·빌드 결과를 제외합니다. `docs/examples/`의 표와 정책은 합성 시연 자료입니다. `초보자_PDF_예제.pdf`는 “Easyflow report page one”, “Second page contains actual text” 두 페이지의 합성 시험 문서이며, 문서 API 회귀 테스트용으로 포함합니다. 고객 원본 PDF는 등록하지 않습니다.

별도 프린터 매뉴얼 실호출 시험은 `A4B_MANUAL_PDF`에 자신의 로컬 PDF 경로를 지정해 `Frontend/scripts/verify-manual-workflow.ts`를 실행합니다. 또는 `A4B_SESSION_ID`로 기존 시험 대화를 이어갈 수 있습니다. 이 시험은 모델 API 비용이 발생하고 원본 PDF는 로컬에만 보관합니다.

`workflow_preprocessing` 전처리 코드·명세는 `Backend/integrations/workflow_preprocessing/`에, 합성 데이터는 `docs/examples/workflow_preprocessing/`에 보존했습니다. 원본의 NFC·공백 정규화·완전 중복 제거·시나리오별 분할·도구 참조 검증을 사용합니다.

```bash
Backend/.venv-agent/bin/python Backend/scripts/import-preprocessing.py
```

Windows는 `Backend\.venv-agent\Scripts\python.exe Backend\scripts\import-preprocessing.py`를 사용합니다. 합성 사례 32→30건, 변환 가능 12·질문 필요 6·어댑터 미지원 12건을 별도 DB 테이블에 저장합니다. 사용자 워크플로우로 자동 등록하거나 모델을 자동 학습하지 않습니다. 사람 검수 상태는 pending입니다.

## 구조

React 화면 → Node API → Python 생성/실행 worker → 공통 SQLite·LangGraph 체크포인트 → 서버 보고서 파일.

- Deep Agents: 생성 대화 및 필요한 업무의 모델·도구 실행
- LangGraph: 생성 분기, 등록된 노드의 실행·대기·재개·체크포인트
- 등록 노드 코드: 표·문서 읽기, 검색, 추출, 조건, 집계, 저장, 검수
- `run_lifecycle.py`: 실행 소유권·시도 이력·종료 복구·보고서 소유권 검사
- `scheduling.py`: 시간대·예약·관리 소스·작업 큐·heartbeat
- `review_decisions.py`: 사람 승인·거절·승인 CSV
- `review_state.py`: 검수 보고서 중복 제거·최신 수정 후보 선택·재사용 검수 기록 수집
- `node_library.py`: 재사용 노드·불변 버전·선택 노드 검사·역할 초안의 확인 후 저장
- `executors/agent_node.py`: 저장한 역할에 따른 입력 조회·답변 작성

## 노드를 이어 연결하는 구조 — v2.2

등록된 업무 노드 16종은 각각 `Backend/agent_builder/executors/<노드 ID>.py`의 실행 함수를 갖습니다. 앞뒤 노드 이름은 실행 코드에 고정하지 않습니다. `bindings`가 앞 단계 출력 포트를 자신의 입력으로 연결하고, `edges`가 다음 실행·분기 경로를 지정합니다. LangGraph가 저장한 연결을 실제 호출로 구성합니다. 한 흐름의 노드 개수는 기존과 같이 최대 15개입니다.

- `filter_sort.settings.execution_plan`: 해당 노드만의 필터·정렬·예외 정책. 같은 종류 노드를 여러 번 쓰면서 각각 다른 조건을 적용합니다.
- `write_result.settings.format`: 해당 저장 노드의 출력 형식.
- `condition`: table·reviews도 전달하며 all_pass/any_revision으로 검수 결과를 분기합니다.
- `compose_answer`: reviews 입력의 검수 의견을 참고해 수정안을 작성할 수 있습니다. 단일 검수의 최신 수정문을 승인 후보로 연결하며, 원래 판정·문제 구절은 변경하지 않습니다.
- `review_summary`: 검수 결과를 approval_state=pending인 보고서 표로 정리합니다. 이 표를 저장해도 승인된 최종 응대는 아닙니다.
- `saved_workflow`: 저장한 에이전트의 ID·버전·출력 노드·출력 포트를 지정해 하나의 노드로 재사용합니다. 앞 table/documents는 저장 흐름의 읽기 입력을 대체하며 text는 실행 요청으로 전달합니다. 입력을 연결하지 않으면 실행 시 명시적으로 추가한 자료 또는 저장된 설정의 자료를 사용합니다. 선택한 업무 출력은 다음 단계에 전달하고, 검수 기록·수정 후보·승인 필요 상태는 출력 포트와 무관하게 실행에 보존합니다.

재사용하는 설정과 하위 의존성은 부모 설정 저장 시 고정합니다. 원래 에이전트를 수정해도 이미 저장한 부모는 기존 버전을 사용합니다. 화면의 노드 클릭으로 개별 설정·연결을 확인하고 처리 단계 로그에서 재사용 흐름의 내부 단계·버전을 펼쳐볼 수 있습니다.

예시 요청:

> 이미 저장한 팀별 금액 합계 흐름 버전 1을 재사용해서, 그 결과에서 sum이 100 이상인 팀만 추린 뒤 JSON으로 A4B 보고서 보관함에 저장해주세요. 새 예약 없이 연결 자료를 그대로 쓰고, 빈 값·비숫자는 실패로 처리하며 중복은 유지해주세요.

현재 재사용은 같은 모델·연결 계정으로 제한합니다. 자기 자신·재귀 호출은 거부하고 중첩은 최대 4단계입니다. 저장된 흐름의 예약은 함께 켜지지 않으며 호출한 부모의 실행에서 처리합니다. 순차 연결·조건 분기·대기/재개와 같은 노드/흐름의 여러 인스턴스를 지원합니다. 병렬 실행과 뒤로 돌아가는 순환 반복은 아직 지원하지 않습니다.

기존 글로벌 execution_plan은 이전 저장 설정의 호환용으로만 유지합니다. 새 노드에 개별 설정이 있으면 그 설정을 우선합니다. 전처리 코드·기존 예약·승인·복구 기능은 유지했습니다.
