## 채택한 결과

같은 GPU·가중치·동결 데이터와 같은 측정기로 실험한 네 건은 전체 요구 성공 **3/4 → 4/4**, 호출 17→15회였다. H21이 종전에 재질문으로 멈추던 단계를 넘어 실제 CSV 실행에 도달해 입력 토큰은 107,673→111,569개, 전체 사례 시간은 313.64→363.59초, 선별 p50은 72.87→110.28초로 **증가했다**. 목표 30초는 이 표본에서 달성하지 못했다. 서비스 전체 p50 및 52/35/신규 30건 평균은 미측정이다.

H32는 의미 추출·검토 4회를 생략해 동일 요약을 두 결과로 전달하면서 **8→4회, 47,178→37,758 입력 토큰, 140.95→114.21초**가 됐다. 같은 결과를 양쪽에서 달성한 H01·H20·H32 세 건의 합계는 14→10회, 입력 80,524→71,104, 출력 2,862→2,158, 전체 265.01→251.85초다. ## 호출별 판단

- **의미 검토**. H32의 첫 추출은 문서 원본을 Gmail로 잘못 지정하고 저장·발송 일부를 누락했다. 두 번째 추출도 독립 산출물과 자료 범위를 충분히 구별하지 못해 거절됐다. 반면 H20의 첫 턴은 추출·검토 두 호출에서 봉인됐고 후속 턴에서 원래 날짜가 유지됐다. 종전 52건의 실제 검토 응답 17개 중 7개, 종전 독립 35건의 13개 중 8개는 `faithful=false`였다. 이는 검토 모델의 **거절 빈도**다. 검토가 없을 때의 오답률은 별도 대조군 실측이 없어 미측정이다. 전체 검토를 제거하면 거절된 후보도 후속 상태에 들어갈 수 있다. 확정할 수 있는 복합 계약이 모든 요청 절과 선행 관계를 설명하는 경우에는 그 계약의 사용을 평가할 수 있다.
- **도구 지원**. H32에서는 `example.invalid` 주소의 실제 배달 가능성과 도구의 설계 가능성을 혼동해 첫 응답이 미지원이었다. 기존 재검토 경로가 카탈로그를 다시 읽고 지원으로 바꿨다. 수정 전 스냅샷과 동결 H32를 사용해 전송 직전 payload를 오프라인 재구성했다. 카탈로그 대조용으로 재구성한 Capability 사용자 payload 24,006자 중 도구 설명은 62개·18,285자다. 관련 도구만 남기면 지원 공백으로 오인할 수 있다. 전체 ID/가능 동작의 발견과 승인 전 실제 계약 대조를 유지해야 한다.
- **요구사항 재추출**. H32의 Qwen 응답은 원문에 명시된 형식과 수신자를 다시 물었다. 실제 Requirement Ledger는 원문 근거에서 이 두 항목을 복원해 질문 0개와 두 소비자로 확정했다. H20 후속 수량 편집은 입력 fingerprint 변경으로 동일 장부 캐시를 그대로 사용하지 않았지만 이전 검토 결과와 최초 날짜를 재사용해 모델 호출이 0회였다. H01·H21·H32의 해당 Requirement 진입에는 이전 장부가 없었다.
- **긴 계획 입력**. 위 H32 Planner의 재구성된 시스템 문구는 11,977자, 근거·상태 컨텍스트 메시지는 21,862자, 응답 형식 JSON 스키마는 34,737자였다. 컨텍스트에 전체 도구 발견 목록 10,876자, 선택한 상세 계약 3,133자, SVM 추천 1,709자가 있다. 표 관련 부가 설명 623자도 문서 요약 요청에 들어왔다. `request_requirements.tasks[*].spec`과 `required_execution_contracts.specs`는 값과 순서가 일치했다. 문자·JSON 크기는 중복 위치를 찾는 단서다. tokenizer 입력으로 환산하지 않았으며 실제 토큰은 서버/SDK 값 13,619개다. 기존 생성기는 상세 계약 조회 기능과 전체 도구 발견 목록을 분리하고 있었고, 원문 근거와 이전 메시지의 별도 사본은 후속 검증에도 쓰인다. [오프라인 프롬프트 구성 대조](../runtime/final-qwen-performance/candidate-work/prompt-shapes.json)
- **Repair**. 위 H32는 의미 후보 재추출과 미지원 판정 재검토가 있었지만, Validator 이후 Workflow Planner에 다시 들어간 적은 없다. H32의 그 이전 실패 trace에는 첫 발송 초안의 수신자 충돌을 검증한 후 같은 턴에 한 번 재생성한 기록이 있다. 현 코드에서는 검증된 상수와 요약 출력이 모든 요구를 다시 만족하는 경우에만 결정적으로 보정하고, 추가 주소·부수효과·서로 다른 요약 생산자는 거절한다. 남은 사용자 선택은 질문, 구조·형식 오류는 제한된 생성 재시도, 전송 오류는 실패로 구분한다. 이 네 사례만으로 재시도 정책 전체를 없앨 근거는 없다. [수정 전 실패 초안과 Repair](../runtime/generalization-focused/h32-focused.json)

종전 52·35개 원본의 같은 턴에서 Validator가 재진입한 횟수는 각각 5회와 9회였다. **14회 모두 첫 검증과 재검증의 오류 배열이 순서까지 같았다.** 재생성 모델 호출은 총 471.09초, 입력 177,997토큰·출력 7,002토큰이었다. 해당 턴 8개(M09, X05, H01, H05, H14, H18, H19, H29)는 장부에 `other` 업무가 있었다. 그 계약은 현재 coverage에서 실행 노드에 대응시킬 수 없어 고정된 장부를 그대로 두고 초안만 고쳐서는 해당 오류를 해소할 수 없다. 나머지 여섯 턴은 재시도가 실패한 관측만 있고 첫 시점부터 결정적으로 불가능했다는 증거는 없다. 현재 전후 4건에서 이 과거 비용을 절감했다고 산정하지 않았다.

이 근거에 따라 일반 supervisor가 동일한 확정 장부의 `other/unverified`를 위해 초안만 재생성하던 분기를 수정했다. 이전 Validator의 검사에서 해당 업무가 미검증이었을 때만 현재 장부·사용자 상태·초안을 기존 coverage 함수로 다시 검사한다. 두 검사 모두 같은 ID의 검증 불가능한 업무를 보고할 때 실패 상태·기존 오류와 초안을 유지하고 재생성을 생략한다. 오래된 판정, 실제 사용자 질문, 지원 불가 응답과 정상 복구 가능한 설정 오류의 경로는 회귀 사례로 확인했다. 같은 기존 실패 8건 중 6건은 과거 장부를 현 계약에서 다시 검증하고 원래 첫 초안을 통과시켜 `repair → invalid` 전환을 관측했다. X05/H29의 과거 장부는 최신 순서 검사에서 거절돼 재봉인하지 않았다. 해당 6건의 과거 체크포인트를 재생한 결과이며 현재 성공 사례의 흐름이 실패로 바뀌었다는 의미는 아니다. [원본 체크포인트 재생 결과](../runtime/final-qwen-performance/repair-checkpoint-replay.json)


## 비교 계측의 의미

| 값 | 집계 경계 |
|---|---|
| 사례 전체 | 새로운 서비스 세션부터 마지막 응답 및 지정된 로컬 합성 저장·실행까지의 단조 시계 시간. 모델 접속 probe, 프로세스 기동, 최종 집계 파일 기록과 사용자의 답변 대기는 제외 |
| 호출 벽시계 | 실제 Ollama 또는 LangChain 모델 래퍼 진입부터 응답 처리까지. SDK 응답은 메시지 usage_metadata, 네이티브는 prompt_eval_count/eval_count. 둘을 중복 집계하지 않음 |
| Ollama 서버 시간 | 네이티브 HTTP 응답의 total_duration. 새 계측은 load_duration, prompt_eval_duration, eval_duration을 ns→초로 변환. SDK 플래너는 서버 내부 값이 없으면 공란. 서버 총시간과 세부 구간, 호출 벽시계는 포함 관계 |
| 워커 CPU | time.process_time으로 사례·단계·호출 각각의 워커 프로세스 CPU 사용 시간을 관측. Python 인터프리터, C 라이브러리, 프로세스 내부 쓰레드를 포함하며 Ollama 프로세스의 GPU/CPU와 사용자의 대기 시간은 제외 |
| 동기 스냅샷 | 모델의 시작·dispatch 직전·종료에서 기록하는 콜백의 벽시계·프로세스 CPU. 응답 원문 정제·직렬화와 임시파일 기록·원자적 교체를 포함. 단계/사례에 포함되는 측정치이며 호출 종료 후 콜백은 호출 벽시계에서 제외됨 |
| 단계 잔여 | 단계 벽시계에서 하위 호출 벽시계를 뺀 값. 검증, 프롬프트 구성, I/O, 계측 및 스케줄링을 포함. 인터프리터 CPU 또는 순수 추론 시간과 서로 다른 단위 |
| 캐시·재시도 | Requirement 진입 전후 장부 fingerprint/digest, 의미의 확정·재사용 진단, 실제 호출 인덱스와 같은 턴의 Planner 재진입으로 판정. HTTP를 쓰지 않은 결정적 계산과 모델 캐시 적중을 구분. SDK에 표시되는 cache_read=0은 서버 KV 캐시 적중률을 입증하지 않음 |

기존 실험을 그대로 보존하고, 새 전후 비교는 동일 계측 manifest `b0babec95e78a97ec573573a7ddd73b548fb981b02d15514562813bb782dced1`를 사용한다. 환경은 로컬 Ollama 0.40.16, RTX 4060 Ti 8GB(드라이버 610.88), 공개 Qwen3.5 9B Q4_K_M이다. 모델 태그 digest는 `dfd32b09718e2aa05f622795b2ab575efc817c6129928209c532c55023f4f2df`다. 기본 seed 42·temperature 0·context 32,768·출력 상한 4,096·top_k 20·top_p 0.8, 같은 동결 JSON과 순서(H01, H20, H21, H32)를 사용했다. 수치 재현은 작업 트리 루트에서 `python scripts/verify/profile-qwen-stages.py <실측 JSON> --case H32`로 가능하다. 사례 옵션을 생략하면 그 실행 파일 전체를 집계한다.

### 승인과 로컬 합성 출력의 별도 관측

실제 서비스의 승인 대기와 사용자 승인·저장을 구분했다. H20·H32는 READY에서 종료하므로 실제 승인·실행은 없다. H01·H21은 동결 오라클이 필요한 경우에만 worker의 confirm과 test를 호출한다. 라이브 전체 시간에 포함된 두 동작은 각각 독립 타이머가 없었다. 같은 소스의 **모델 없는 서비스 재생**에서 임시 SQLite에 실제 기록한 보조 측정은 다음과 같다. 라이브에서 실행이 막힌 사례에 이 보조 측정 시간을 더하지 않는다.

| 오프라인 서비스 재생 | confirm 벽시계 / CPU | 합성 test 벽시계 / CPU |
|---|---:|---:|
| 수정 전 H01 | 0.0987 / 0.0625초 | 0.0657 / 0.0781초 |
| 수정 전 H21 | 0.0812 / 0.0781초 | 0.0449 / 0.0469초 |
| 최종 후보 H01 | 0.1345 / 0.1094초 | 0.0961 / 0.0781초 |
| 최종 후보 H21 | 0.0765 / 0.0781초 | 0.0498 / 0.0156초 |
