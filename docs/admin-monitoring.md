# 관리자 모니터링

관리자는 기존 `a4b.users.role='admin'`을 사용합니다. 로그인마다/요청마다 기존 인증 모듈이 회원 상태를 다시 읽으며, 이메일을 로그인 허용 목록으로 사용하지 않습니다. 일반 회원·비로그인·비활성 관리자는 `/api/admin/*`에 접근할 수 없습니다. 로컬 비인증 모드도 관리자 접근을 허용하지 않습니다.

## 화면과 API

관리자 로그인 후 사이드바 **모니터링** 또는 `/?screen=monitoring`에서 엽니다.

- 최근 24시간 / 7 / 30 / 90일, 생성·실행·문서 처리, 실패·차단·전체 결과, 처리 상태로 필터링합니다.
- 요청 ID·고유 회원 ID·노드·오류 코드로 검색하고 25건씩 조회합니다. 목록에는 로그인 이메일을 표시하고, 이메일이 없으면 기존 회원 ID를 표시합니다. 검색은 기존 ID·노드·오류 기준을 유지합니다.
- 요약과 오류 집계는 기간·유형 기준이며, 목록 검색·결과·처리 상태 필터와 구분합니다. 추가 질문 대기와 차단을 실패율에 합산하지 않습니다. 테스트 요청은 별도 구분 정보가 없어 포함됩니다.
- 상세 화면은 단계 기록(최대 100개), 오류 사유, 추적 ID·모델·배포 버전·검증 필드/유형을 표시합니다. 과거 데이터는 새 진단 필드가 없을 수 있습니다.
- 처리 상태/메모 변경은 revision 비교로 동시 수정 충돌을 감지하고 변경자를 기록합니다. 최신 30개 변경 이력을 표시하며 DB에는 전체 이력이 남습니다.

`GET /api/admin/monitoring?days=7&kind=all&status=failed&triage=all&page=1&q=`

`GET /api/admin/monitoring/{generation|execution|document}/{id}?days=7`

생성 요청의 API `id`는 `회원ID:요청ID` 형태입니다. 작업 공간이 다른 동일 요청 ID를 구분합니다.

`PATCH /api/admin/monitoring/{kind}/{id}`: `{status,note,revision}`. status는 `unreviewed`, `investigating`, `resolved`; note는 최대 2,000자입니다. 기존 same-origin 검사를 적용합니다.

## 데이터와 권한

`009_admin_monitoring.sql`과 후속 `010_admin_monitoring_fixes.sql`·`011_monitoring_document_failures.sql`·`012_monitoring_request_context.sql`을 DBA 마이그레이션 계정으로 순서대로 적용합니다. SECURITY DEFINER 함수는 전용 NOLOGIN·NOBYPASSRLS 역할 `a4b_monitor_owner`가 소유합니다. RDS의 `postgres`도 BYPASSRLS가 없을 수 있으므로, 이 전용 역할에만 생성 이력 SELECT와 처리 이력 접근 정책을 부여합니다. 앱에는 이 역할의 멤버십을 부여하지 않습니다. 앱 연결에는 기존 `a4b_app`을 사용하며 DBA 연결을 앱 런타임에 전달하지 않습니다. 함수는 서버가 세션에서 가져온 회원 ID의 현재 관리자/활성 상태를 검사합니다. 이 함수의 actor 인자는 외부 HTTP 요청에서 받지 않습니다. 일반 작업 공간 RLS 정책은 변경하지 않습니다.

목록 함수는 생성 요청, 실행/노드, 문서 버전의 진단 필드만 투영합니다. 상세에서만 별도 관리자 함수로 저장된 요청 입력과 연결된 사용자·AI 대화의 텍스트를 조회합니다. 문서 본문·도구/시스템 메시지·첨부·전체 입출력 JSON은 전달하지 않습니다. Node에서 필드를 다시 제한하고 알려진 비밀값, 자격 증명 패턴, URL, 본문 속 이메일 등을 마스킹합니다. 회원 식별용 로그인 이메일은 별도 회원 조회 결과에서만 표시합니다. 원문 예외 문자열을 새로 기록하지 않고 Pydantic 오류의 위치/유형과 HTTP 상태만 수집합니다. 운영 메모에도 마스킹을 적용하지만 민감한 원문은 입력하지 마세요.

신규 실행 실패와 생성 요청에는 `diagnostics`가 저장됩니다. 이미지의 `/app/.a4b-release`에 빌드 커밋을 기록하며, 파일이 없는 개발 환경만 `A4B_RELEASE`를 사용합니다. 기존 컨테이너 환경이 재사용되어도 배포 버전이 이전 값으로 고정되지 않습니다. 로컬 미설정과 과거 기록은 미기록으로 표시합니다. 모델별 형식 오류의 상세가 제공되지 않는 예외는 예외 유형까지만 확인할 수 있습니다.

인증 실패·기록 시작 전 요청 실패 및 별도 Node 워크플로 엔진의 SQLite 실행은 이 첫 버전의 RDS 모니터링 범위에 포함되지 않습니다. 기존 실행·생성 이력의 자동 삭제나 서버 로그 수집기를 추가하지 않습니다.

## PR #129 후속 수정 (010)

운영에 적용된 009는 변경하지 않습니다. `010_admin_monitoring_fixes.sql`을 등록하고 앱의 필수 스키마 버전을 10으로 올렸습니다. 기존 배포 스크립트가 새 이미지로 교체하기 전에 root 전용 DBA 설정으로 후속 마이그레이션을 실행합니다. 이 수정 작업 중 운영 010 적용이나 배포는 실행하지 않습니다.

- 실행 조회는 `coalesce(finished_at, created_at)`으로 기간을 비교합니다. 생성 이력은 종료 시각 우선의 `monitor_at timestamptz`를 백필하고 트리거로 유지합니다. 종료 시각이 없는 기록은 시작 시각을 사용합니다. 목록 정렬과 표시에도 같은 시각을 사용하며 상세의 시작/종료 시각은 보존합니다.
- 생성 이력의 문자열 인덱스를 날짜형 인덱스로 교체합니다. 백필은 기존 NOLOGIN 소유자 역할과 임시 UPDATE 정책으로 FORCE RLS 환경에서도 수행하고, 해당 권한/정책은 즉시 회수합니다. 전체 백필과 인덱스 생성 동안 테이블 잠금이 발생하므로 이력이 큰 환경에서는 배포 시간을 고려해야 합니다.
- 처리 상태 저장은 종류와 선택 테이블 존재 여부로 분기합니다. 테이블이 없는 종류는 record-not-found, 생성 요청은 정상 저장됩니다.
- 보고서 저장·검수 보고서 저장·검수 방어 실패도 최종 저장 전에 진단 정보를 채웁니다. 이미 수집한 예외 진단은 덮어쓰지 않습니다.

후속 SQL 회귀 테스트는 비어 있는 전용 로컬 DB(이름 끝 `_review_test`)에 `A4B_MONITOR_MIGRATION_TEST_DATABASE_URL`을 설정해 `Backend/api/tests/admin-monitoring-migration.test.ts`를 실행합니다. 테스트는 자체 `a4b` 스키마를 생성/제거하므로 공유 DB를 사용하지 않습니다. 업무 테이블 유무, 009→010 백필, 시간대 변환, 업데이트 트리거, 실제 인덱스 실행 계획, 오래 대기한 실행의 최근 실패 포함을 검사합니다.


## 추가 리뷰 수정 (011)

`011_monitoring_document_failures.sql`은 문서 버전의 uploaded/processing → failed 전환을 AFTER 트리거로 관찰하여 별도 RLS 보호 테이블에 실제 관측 시각을 기록합니다. 문서 버전의 불변 스냅샷과 기존 상태 전이 검증은 수정하지 않습니다. 조회·집계·발생 시각·종료 시각은 이 실패 시각을 사용합니다. **011 적용 전에 이미 실패한 문서는 정확한 실패 시각이 없으므로 생성 시각으로 대체하고 종료 시각은 미기록으로 둡니다. 과거 실패 시각을 소급 복원하지 않습니다.**

새 실행 시도 시작 시 이전 diagnostics를 초기화합니다. 재시도가 성공하면 과거 진단이 남지 않고, 후반 저장 실패이면 현재 배포 버전으로 새 진단을 채웁니다. 마이그레이션 테스트 정리는 이번 테스트가 직접 만든 스키마 OID와 일치할 때만 삭제하며, 기존 스키마 생성 충돌 시 표와 데이터가 보존되는 회귀 검증을 추가했습니다.

운영에는 009까지만 적용한 상태이며 010·011은 팀장의 PR 병합 후 배포 마이그레이션 단계에서 적용합니다. 이번 수정 작업은 운영 DB 변경·병합·배포를 실행하지 않습니다.


## 실행 중단 진단

실행 시작 시 추적 ID·모델·배포 버전만 `attempt_metadata`에 저장하고 업무 실행 상태에도 보존합니다. 프로세스 종료·임대 만료 복구는 이 저장값으로 `InterruptedExecution` 진단을 생성하므로 복구 작업자의 새 모델이나 배포 버전으로 덮어쓰지 않습니다. 재시도마다 새 시작 시점의 값을 저장하며 이전 소유자 토큰의 중단 요청은 무시합니다. 시작 메타데이터가 없는 과거 실행은 기존 실행 모델과 추적 ID만 사용하고 배포 버전은 미기록으로 둡니다. 추가 DB 마이그레이션은 필요하지 않습니다.


## 이메일·요청 입력·대화 조회 (012)

기존 목록과 오른쪽 상세 배치를 유지합니다. 목록 회원 ID 자리에 로그인 이메일을 표시하고 상세에 요청 입력과 기본 접힘 상태의 **대화 내역 펼치기**를 추가합니다. 저장된 입력이나 연결된 대화가 없으면 미기록으로 표시합니다.

- 생성 요청은 회원 ID와 요청 ID를 함께 사용하고 저장된 session_id로 연결합니다.
- 실행 요청은 input_json.request를 표시하고 **실제로 실행한 버전**의 agent_versions.session_id로 대화를 찾습니다. 최신 버전으로 대체하지 않습니다. 세션 소유 회원과 실행 워크플로도 일치해야 합니다.
- 대화는 현재 저장된 설계 세션의 사용자·AI 텍스트이며 실패 시점 스냅샷이 아닙니다. 실패 이후 내용이 포함되거나 저장 전 중단된 내용이 없을 수 있음을 화면에 안내합니다.
- 생성 요청 입력은 저장 시 최대 4,000자이며 신규 기록은 생략 여부를 함께 저장합니다. 과거 기록은 저장 한계·생략 여부 미기록·원문 복원 불가를 안내합니다. 실행 요청 입력은 표시 시 최대 8,000자, 최근 대화 40개 및 메시지별 4,000자를 표시하고 생략 여부를 알립니다. 문서 처리 요청에는 입력·대화 미기록을 표시합니다.
- 비밀번호·토큰·키 패턴과 환경에 등록된 비밀값 등을 서버에서 마스킹합니다. 임의의 자연어 비밀정보를 모두 자동 식별할 수 있는 것은 아닙니다. HTML은 텍스트로 렌더링합니다.
