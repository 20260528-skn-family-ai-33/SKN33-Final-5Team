# 되묻기 조건 검사 개발안 — 2026-10-26

## 적용 범위와 현재 상태

첫 개발 범위는 **한 단계의 상수 값 선별·중복 제거·일/주 예약**이다. 도구 추천 SVM은 변경하지 않는다. 여러 필터의 논리식, 열끼리 비교, 집계, 일반 문서 작성, 작업 종류 변경은 아직 이 계약의 완전 검증 범위가 아니다. 지원 범위 밖을 업무상 미지원으로 단정하지 않고 검토 대상으로 보류한다.

이전 실제 모델 평가의 추출 계약은 `condition-contracts-v5`다. 실제 요청의 주 업무 하나를 `operation`으로 선택하며 여러 업무가 섞이면 mixed로 보류한다. 초기 v1~v3의 다중 operations 배열에서는 요청하지 않은 업무까지 선택하는 오류가 발생해 형식을 단순화했다. v5는 시간대의 명시 근거와 좁은 표현의 결측·중복·출력 정책 보존 규칙을 추가했다. 이전 실패 결과는 별도 보존한다. 이 변경을 독립 평가나 단일 프롬프트 요소의 효과로 해석하지 않는다.

`A4B_CONDITION_MODE=off`가 기본값이며 기존 설계 경로에 추가 모델 호출이 없다.

| 모드 | 동작 |
|---|---|
| off | 기존 동작. 별도 조건 모델 호출 없음 |
| shadow | 조건 판정과 설정 반영 검사 결과를 trace에 기록. 기존 분기는 변경하지 않음 |
| enforce | 미정 조건은 질문, 시스템·출력 오류는 보류, 확정 조건과 설정의 불일치는 수정 또는 저장 차단 |

새 조건 판정은 앱에서 선택한 모델을 사용한다. Ollama에서는 기존 native transport를 사용하며, 다른 연결은 기존 model factory를 사용한다. 실제 평가된 provider/model 조합만 검증됐다고 표현한다. 운영 기본값이나 모델 가중치를 변경하지 않는다.

### 그래프 구성 방식의 별도 실험

`A4B_CONDITION_PLAN_MODE=llm`이 기본이며 기존 Deep Agent/direct 생성기를 사용한다. 이 경로의 실제 로컬 Qwen 시험 1건에서는 인용·연결 오류로 저장 전에 차단됐다.

`A4B_CONDITION_MODE=enforce`와 `A4B_CONDITION_PLAN_MODE=template`를 함께 선택하면 대표 표 업무의 확정 조건으로 코드가 read_table → filter_sort → write_result 구조를 구성한다. 예약은 read_table → write_result와 별도 schedule 설정이다. Qwen은 조건 추출·답변 반영을 담당하고, 질문 문구와 그래프 연결은 코드가 구성한다. **일반 LLM 그래프 생성 성공으로 세지 않는다.**

템플릿은 추가 모델 호출이 없으며, 표 자료를 하나로 식별할 수 없거나 정렬 등 범위 밖의 요청이면 보류한다. 자료/검증 오류를 LLM에 넘겨 임의 수정하지 않는다. 대표 템플릿의 실제 모델 시험 1건은 질문→답변→시험용 확인→저장→실행까지 성공했고 100만원 초과의 경계값 제외와 결과 행을 대조했다. 실제 사용자의 승인·UI 시험이나 일반 업무 전체 성공률은 아니다.

## 조건 정의표

| 작업 | 필수 업무 조건 | 조건부 항목 | 질문하지 않는 내부 항목 |
|---|---|---|---|
| 상수 선별 | 비교 열·비교 연산·기준 값 | 사용자가 지정한 결측/중복 정책·출력 형식은 보존·감사 | 포트·노드 ID·내부 숫자 변환 |
| 중복 제거 | 중복 판단 열·보존 정책 | 명시한 출력 형식·결측 정책 | 임의 기본 보존 정책으로 자동 확정 금지 |
| 예약 | daily/weekly·시·분·시간대 | weekly이면 요일 필수 | ‘오전 8시’의 분=0 등 명시 시각의 정규화 |

조건 상태는 specified / missing / conflict다. 모델이 작업 종류를 식별하면 코드가 필수 조건의 누락을 추가한다. **작업 종류 자체의 오인식이나 전체 사용자 조건 누락까지 코드만으로 완전히 해결하지는 않는다.**

필수 상태가 해결되지 않으면 clarify다. 명시된 외부 동작에 등록 도구가 없으면 unsupported다. 정상 입력·범위 내 작업·필수 조건 해결 상태는 ready다. 모델/계약/조회/파싱 장애는 별도 system_error, 대표 범위 밖 또는 취소는 manual_review로 보류한다. ready도 사용자 확인·저장·실행 성공을 의미하지 않는다.

## 입력·출력 계약

입력은 원래 사용자/assistant 대화, 실제 자료 ID·열·본문·페이지·프로파일, parser_status·processing_status·warnings·parser_metadata, 자료 version/hash, 이전 조건 ledger, 대기 질문과 답변 이력이다. `source_health.db_status`와 `messages_loaded`는 외부 어댑터가 조회 결과를 전달하는 필드다. 현재 worker의 실제 DB 예외는 기존 오류로 반환되며 빈 대화로 바꾸지 않는다. AWS RDS 장애 복구를 구현하거나 검증했다는 뜻은 아니다.

자료에 version/hash가 없으면 본문·페이지·열의 내용 해시로 변경 여부를 비교한다. 요일은 명시적 원문 요일이 하나일 때 월요일=0 규칙으로 코드 정규화하고 변경 내역을 남긴다. 모호한 날짜/요일의 의미를 코드가 추측하지 않는다.

‘빈 값은 오류/제외/유지’, ‘중복 유지’, ‘CSV/JSON으로 저장’ 등 좁게 정의한 원문 구절은 모델이 누락해도 코드가 보존한다. 부정·같은 턴의 상충 구절은 임의 확정하지 않는다. 이 규칙은 한국어 전체 의미를 해석하는 파서가 아니며, 다른 표현은 추가 검수와 평가가 필요하다.

출력 ledger는 operations, key별 상태·값·원문 근거, decision, unresolved, questions, issues, resource_versions다. JSON 스키마·ID 소속·일부 값/범위 검사를 수행한다. 정확한 인용이 있다는 사실은 의미적 정답의 충분조건이 아니다.

질문 전에는 저장된 전체 페이지/본문을 대상으로 단어 검색하여 상위 8개 구간을 고른다. 검색은 의미 검색이 아니며, 검색 결과가 없거나 문맥 일부만 반환돼도 ‘문서에 답이 없음’을 입증하지 않는다. scanned_chunks / returned_chunks / complete_context를 함께 기록한다. OCR·PDF 변환기를 변경한 것은 아니다.

## 답변과 재개

대기 질문마다 세션·대화·자료 버전에 의존하는 ID를 부여한다. `question_id`가 있으면 현재 세션의 대기 질문인지 검사한다. 기존 자유 답변 UI도 유지하며 이 경우 후보 질문 목록과 답변을 연결해 모델이 어떤 조건이 해결됐는지 다시 판단한다. 질문 ID만으로 답변의 의미적 정확성을 보장하지 않는다.

Node API의 선택 입력은 `questionId`이며 Python worker에는 `question_id`로 전달한다. 현재 화면의 자유 답변 전송에는 ID가 없어도 작동한다. 질문별 전용 UI를 새로 구현한 것은 아니다.

다른 세션/지난 질문의 ID는 입력으로 반영하지 않는다. LangGraph interrupt의 재실행 특성 때문에 잘못된 resume 입력을 노드 예외로 남기지 않고 재질문한다. worker는 interrupt 호출 전에 ID를 검사한다. 기존 session revision 검사는 중복 제출을 거부한다. 재시작 후 같은 thread_id로 저장 상태를 복구한다.

기존 확정 조건은 재질문하지 않고 보존한다. 값 변경에는 마지막 성공 판정 이후의 사용자 변경 근거가 필요하다. 사용자의 일부 답변만 들어오면 남은 조건을 계속 질문한다. 명시적 작업 전환/취소·문서 교체의 전체 제품 UX는 추가 검토 대상이다.

## 생성·저장 검사

확정 조건은 Deep Agent/direct 생성기의 문맥으로 전달한다. 생성 뒤 filter_sort 설정·예약·출력 형식과 대조하고 불일치하면 기존 수정 경로로 보낸다. 저장 직전 같은 검사를 반복하여 잘못된 초안이 확인만으로 저장되지 않게 한다.

초기 범위에서는 조건의 존재를 확인하지만 전체 흐름에서 그 조건이 나중에 다른 노드로 무효화되는 모든 경우까지 증명하지 않는다. 실제 행 결과와 기대값 대조가 필요하다.

## 평가와 승인 기준

1. 코드 검사: 형식·범위·외부 근거 ID·상태 일관성·장애 분기·상태 보존·저장 차단.
2. 통합 검사: 질문 후 재시작·올바른 답변·사용자 확인·저장·실제 표 실행. 모델 응답 fixture 사용 여부를 명시.
3. 실제 Qwen: 버전·digest·설정·데이터/소스 해시를 고정하고 기존 판정과 후보를 비교. 모든 오류/timeout도 분모에 포함.
4. 사람 검수: 개발 사례 정답과 질문 품질을 검수하고 새 원본으로 최종 평가셋 분리. AI 작성 사례를 human gold로 표기하지 않음.

지표는 분기 일치, 필요한 질문 누락, 불필요한 질문, 미지원 오판, 조건 값/답변 반영, 최종 업무 결과, 호출 오류, 시간·토큰을 구분한다. 초기 소규모 개발 점수를 서비스 정확도나 독립 평가로 일반화하지 않는다.

실제 모델 검증과 사람 검수 전에는 기본 모드를 변경하지 않는다. LoRA는 입력·상태 문제를 제거한 후에도 남는 오류가 재현되고, 학습/평가 분리를 확보했을 때 검토한다. 이번 작업에서 학습·배포·Git push는 수행하지 않는다.

## v6: 미정 답변과 실행 자료 안내

현재 개발 계약은 `condition-contracts-v6-input-resolution`이다. 질문에 대한 단독 미정 답변은 코드에서 확정값으로 사용하지 않으며, 대안 안내와 보류 후 재개를 제공한다. 필터 설계의 실행 자료와 예약 설계의 관리 자료를 구분한다. 수동 실행 API는 시작 전 필수 경로의 파일·열·파싱 상태를 확인한다.

추가 25개 동작 검사와 Python 전체 384개가 통과했다(선택적 SVM 검사 1개 제외). 실제 모델의 이번 프롬프트 변경 효과는 측정하지 않았으며 v5의 개발 점수를 v6의 성능으로 해석하지 않는다. 기본 모드는 off다. 조건 분기 이후의 파일과 내부 런타임 직접 호출은 기존 실행 시 검사를 유지한다.

## v7: 확인 화면 수정과 응답 규격 복구

현재 개발 계약은 `condition-contracts-v7-review-repair`다. 위 v6 결과는 이전 검사 기록이다.

조건 검사 enforce 상태에서 확인 화면의 수정 답변은 condition_check로 돌아간다. 재판정한 조건과 초안에 다시 사용자 확인이 필요하다. off 모드의 기존 대화 경로는 유지한다.

조건 판정 노드는 모델 응답의 JSON·스키마 규격 오류에 한해 수정 요청을 최대 1회 보낸다. 실제 원문 근거 목록을 유지하고 오류 항목만 전달한다. 모델 연결 실패에는 이 재호출을 적용하지 않는다. 실패가 남으면 기존 확정 조건과 `validated_user_turn`을 보존한 system_error로 중단하고 저장을 막는다. 일반적인 재시도 답변 뒤에도 마지막 성공 판정 이후에 사용자가 실제로 제시한 변경 근거를 사용할 수 있다.

2026-10-26 Python 회귀 검사 389개 통과, 선택적 SVM 검사 1개는 joblib 미설치로 제외했다. 실제 qwen3.5:4b 조건 판정 개발 사례 8/8, 입력 장애 주입 2/2가 예상 분기와 일치했다. 코드 템플릿 경로의 최초 통합 결과는 2/3이고, 실패한 조건 변경 사례는 수정 후 재시험에서 실제 저장 JSON까지 정답과 일치했다. 재시험에서는 규격 복구 재호출이 발생하지 않았으며 해당 복구 분기는 고정 응답 회귀 검사로 확인했다.

별도 Qwen 직접 전체 흐름 생성 1건은 연결·인용 오류로 저장이 차단됐다. 템플릿 경로의 성공을 일반 생성기의 성공률로 해석하지 않는다. 모두 합성 개발 사례이며 실제 사용자 승인·업로드 파서·RDS 장애 검증은 아니다. 조건 검사 기본값 off 유지. 상세 기록은 작업공간 `research/a4b_clarification_live_20261026/REPORT.md`에 보관한다.

## v8: 단일 중복 제거의 변형 범위 제한

현재 계약은 `condition-contracts-v8-dedup-scope`다. `operations=['deduplicate']`인 단일 대표 업무에서는 filter_sort 실행 설정에 추가 filters/sort가 있으면 조건 감사와 저장 직전 검사에서 차단한다. 결과 행이 우연히 같아도 추가 변형을 승인하지 않는다. 모델의 초안에서 해당 설정을 자동 삭제하지 않는다.

이 계약은 중복 제거에 선별·정렬까지 결합한 복합 요청을 승인하는 계약이 아니다. 복합 요청에는 별도의 조건 정의와 검증 범위 확장이 필요하다. 조건 검사 off 경로에 전역으로 새 제한을 거는 것은 아니다.

선택 direct 프롬프트 v5에서는 조건 장부의 내부 키를 업무 의미·실제 값·열 여부·근거로 읽기 전용 투영한다. 단일 중복 제거의 생성용 스키마에도 같은 filters/sort 제한과 이미 확정된 정책 값을 전달한다. 원래 조건 장부·공개 AgentDraft·모델 가중치는 변경하지 않는다. 이는 코드 계약 보조이며 Qwen 단독의 무제약 생성 성능으로 해석하지 않는다.

이번 요구사항별 재검증 기록은 작업공간 `research/a4b_requirement_audit_20261026`에 보관한다. 기본 조건 검사 off 및 기본 deepagent/v1은 유지한다. v7 이하 기록은 당시 코드의 개발 시험 결과로 보존한다.

## 2026-10-27 후속: 판정 출력 제약과 최신 변경

출력 계약 이름은 `condition-contracts-v8-dedup-scope`를 유지한다. Ollama 판정 디코더에서는 specified 조건에 값·근거를 요구하고, missing/conflict 값은 null로 구분한다. 응답 후 기존 근거·상태 검증도 계속 적용한다. 최신 사용자 발언과 해당 근거 ID를 별도 문맥으로 제공해 과거 기준보다 명시적 변경을 우선하도록 안내한다. 사용자만 결정할 수 있는 값을 코드가 임의 확정하는 보완은 아니다.
