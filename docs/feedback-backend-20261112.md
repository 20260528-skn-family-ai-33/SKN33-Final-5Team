## 추가 실행 요청의 지원 범위

- 기존 조건 처리 결과에 추가 선별·정렬을 적용한다. 저장된 조건을 대체하지 않는다.
- 예: `주문상태 = 완료; 주문금액 >= 100000; 주문번호 오름차순`.
- 예: `금액 100,000 이상`, `금액 숫자 내림차순`. 구분자는 세미콜론 또는 줄바꿈이다.
- `완료 주문`과 `완료 주문만`은 같은 조건으로 처리하며 상태/주문상태 열이 하나로 명확할 때 지원한다.
- 조건 구분자는 따옴표 밖의 세미콜론·줄바꿈이다. `상태 = "완료;보류"`처럼 인용한 값 안의 구분자는 셀 값으로 보존한다. 인용 문자열은 따옴표·역슬래시 이스케이프를 지원하며 닫히지 않은 인용과 닫는 따옴표 뒤의 잔여 문자는 실행 전에 거부한다.
- `=`/`!=`는 문자 그대로 비교하여 `00123` 같은 식별자를 보존한다. 숫자 대소 비교는 숫자로 비교한다. 정렬은 기본 문자, `숫자`를 명시하면 숫자 정렬이다.
- 필터에 필요한 값이 비어 있으면 임의로 포함하지 않고 오류를 안내한다.
- 기본 read_table/calculate_columns/filter_sort/write_result의 단일 순차 흐름을 지원한다. 분기·중첩·canonical 작업·다중 파일·기존 계산/출력 열 변경은 설정 수정이 필요하다.
- 해석할 수 없는 명시적 변경 요청은 실행 전에 안내한다. 기존 클라이언트의 단순 실행 설명 문장은 호환성을 유지하고 적용되지 않았다는 안내를 남긴다.
- UI나 공개 요청 형식을 추가하지 않았다. 실행 기록의 기존 config_snapshot을 사용한다.

## S5 추가 재현 및 PR #103의 2차 리뷰 반영

### 실제 모델에서 확인한 S5 원인

2026-11-12, 서버 이미지의 배포 커밋은 `33db4e455fe110718dcf5cdfe5905de87c8ca4c3`, 모델은 Ollama의 `a4b-qwen35-9b-final664-pilot32k`였다. 조건·요구사항 검사는 모두 enforce였다. S5 최초 실패와 S7의 잘못된 템플릿 진입은 테스트 계정의 생성 이력과 체크포인트에서도 확인했다.

S5 실패 직전인 `2026-11-12T07:14:20.093099Z`의 저장 상태를 읽어 조건 판정 함수만 재호출했다. 설계·실행 데이터는 저장하지 않았다. 최초 모델 응답과 1회 수정 응답 모두 `filter.field`/`filter.operator`/`filter.value`를 두 벌 출력했다. 첫 묶음은 매출/gte/100000, 둘째는 주문상태/eq/완료였다. 두 응답 모두 `같은 조건을 중복 출력했습니다: filter.field`로 거부됐다. 이는 이번 추가 재현의 응답이며, 보관되지 않은 최초 실패 응답과 동일하다고 단정하지 않는다.

계산 열과 두 필터가 필요한 요청인데 capability 결과가 read_table/filter_sort/write_result만 선택했다. 이 결과에 의존해 단일 필터 계약으로 진입한 것이 재현된 실패의 원인이다. 다음을 수정했다.

- 실제 입력 열을 사용하는 수식 또는 명시적인 계산 요청은 전체 설계기로 전달한다. 계산 도구 추천이 누락돼도 단일 필터 검사에 진입하지 않는다. 날짜·숫자 범위·계산 취소는 계산 요청으로 오인하지 않도록 검사한다.
- 모델이 선택적 duplicate.field를 missing/null로 나열해도 사용자가 중복 처리를 요청하지 않았고 필수 조건도 아니면 중복 기준 질문을 만들지 않는다.
- 조건 계약 실패 시 시도 번호와 안전한 오류 코드를 체크포인트에 보존한다. 모델 원문·키·근거 텍스트는 진단 정보에 저장하지 않는다.
- 계산 도구 추천 누락을 포함한 S5 통합 검사에서 저장·재조회·CSV 실행, ORD-001/ORD-003의 100000/150000 결과, 빈 결과의 헤더와 안내를 확인한다. 모델 응답은 이 통합 검사에서 fixture다.
