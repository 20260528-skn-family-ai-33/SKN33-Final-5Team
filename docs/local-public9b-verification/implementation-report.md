# A4B 오케스트레이션 1차 구현과 검증

**공개 Qwen3.5 9B의 기존 52건에서 전체 요청 성공은 28건에서 35건으로 증가했다. 지정된 실패 7건이 모두 통과했고 기존 성공 28건은 유지됐다. 사전 동결한 독립 35건의 전체 성공은 14건(40.0%)이었다.** 독립군은 필요한 질문을 12/12개 물었지만 실제 답변 반영은 3/6, 워크플로우 업무 충족은 20/63이었다. 확정 조건의 소유권을 분리한 효과는 기존 실패군에서 확인됐으며, 새로운 표현에서의 일반화에는 한계가 있다.

## 측정 버전과 재현

아래 87건은 기준 커밋 `75d46e20f239858f77e8db97571da07b6bdc4fac` 위에 변경을 적용해 측정한 결과다. 측정 당시 앱 파일 manifest의 SHA-256은 `9bf4e43f381bee62e859d7bb9cb9ef7200b086df4ce883d940bbe734f3030b85`다. 이후 이 변경을 `main` 커밋 `977858b5060ba74631c976610cf6810074561b3d`에 통합했다. 통합 커밋에 대한 테스트 결과는 PR 본문에서 확인할 수 있다.

이 PR에는 고정 코퍼스와 판정 기준, 평가·채점 스크립트, 세 지표 요약과 무결성 기록을 포함한다. 상세 응답, 사례별 의미·장부 라벨과 중간 실측 파일은 최초 평가 작업 공간의 `docs/local-public9b-verification/`에 보관했다. 요약의 `source_bytes_sha256`은 그 원본의 해시다.

공개 Ollama Qwen3.5 9B와 백엔드 Python 환경을 준비한 Windows 작업 공간에서는 다음 명령으로 새로운 실측 파일을 생성할 수 있다. 평가기는 설치한 모델의 가중치와 GPU 적재를 확인하고 기존 52건, 독립 35건을 순서대로 실행한다. 각 사례의 의미·장부 평가는 동결한 기준에 따라 새 실행 원본을 검토해 작성한다. [평가 방법과 채점 명령](../local-public9b-rebuild-20261111/evaluation-protocol.md)

## 기준점과 평가 범위

이 작업은 커밋 `75d46e20` 위에 남아 있던 미커밋 리빌딩을 이어서 진행했다. 과거 로컬 공개 9B의 [52개 완료 trace](../qwen-local-public9b-after-complete.json)에 기록된 앱 파일 243개의 SHA-256이 이 커밋의 파일과 모두 일치했다. 작업 시작 당시에는 이 중 14개 파일이 이미 수정되어 있었고 새 모듈과 테스트도 있었다. 분석 문서 `clarification-root-cause-analysis.md`는 작업공간에서 찾을 수 없어 과거 모델 원문, 수용 장부, Validator 결과, 기존 수정 전 테스트 기록을 대조했다.

이번 평가에는 [기존 52개](../qwen-live-evaluation-cases.json)와 이전에 별도 봉인한 [독립 35개](../runpod-custom-rebuild-20261111/independent-evaluation-freeze.json)를 사용한다. 독립 사례는 이번 수정용 예시에서 제외했다. 추론 전에 두 코퍼스, 독립 정답·판정 기준 및 기존 채점기 파일의 해시가 [사전 봉인본](../local-public9b-rebuild-20261111/pre-inference-freeze.json)과 일치하는지 확인했다. 생성 결과는 요청별 분기·질문·실행 설정·의존성·지정된 로컬 합성 실행 결과로 판정한다. 실제 외부 메일을 발송하거나 외부 파일을 변경하는 작업은 평가에 포함되지 않는다.

## 상태의 소유권과 변경 흐름

이전에는 Condition에서 검증한 뒤에도 Requirement 모델이 대화에서 같은 값을 다시 추출했다. R04에서 Condition은 첫 행 보존과 빈 값 오류 처리를 이미 확정했지만 Requirement는 두 정책을 다시 물었다. M05의 모델 후보는 월요일 예약 설명과 화요일을 가리키는 실행값을 함께 반환했다. M04에서는 예약을 두 업무로 기록하고 추천 목록의 `filter_sort`를 필수 처리로 취급했다.

| 단계 | 이번 작업 트리의 계약 |
|---|---|
| Condition 확정 | 사용자 턴, 슬롯 값·근거, 자료 버전과 검증 digest를 함께 확인한다. 명시적으로 답한 슬롯이나 수정한 조건에 변경을 한정한다. |
| Requirement 추출 | 검증된 Condition을 읽기 전용으로 참조한다. 확정 슬롯에 해당하는 spec은 코드가 기존 실행 스키마에 투영한다. 모델은 남은 업무·산출물·누락 질문을 제안한다. |
| 질문과 재개 | 질문 키로 소유 슬롯을 검증한다. 선택한 질문의 ID, 키, 답변, 턴을 해당 소유자의 기존 체크포인트에 연결한다. Condition 값·근거 또는 버전이 바뀌면 Requirement 캐시를 재검증한다. |
| 업무 및 생성 | 같은 요구의 재진술인지 원문·산출물·선행 업무로 확인한 뒤 업무 ID를 부여한다. 도구 추천은 계획 후보를 제공한다. 필수 처리의 이행 여부는 실제 사용자 요구와 입력 연결에서 검증한다. |
| 검증 및 저장 | 초안의 설정·연결·의미를 검사하고 저장 게이트에서 현재 장부와 승인 상태를 재확인한다. Qwen, LangGraph, 도구 추천 ML, 생성기, Validator, 승인·저장·실행 경로를 사용한다. |

확정 조건의 값과 증거는 기존 Condition Ledger에 있다. Requirement에는 기존 스키마가 실행·검증에 사용하는 spec과 업무 출처가 남는다. 이 spec은 읽기 전용 투영으로 다시 계산하고 현재 Condition digest와 대조한다. 동일 정보를 개별적으로 갱신할 수 있는 제3의 상태 저장소는 추가하지 않았다.

| 입력·오류의 구분 | 처리 |
|---|---|
| 확인한 조건과 명시적 수정 | 현재 턴·원문·자료 근거로 검증된 값만 사용한다. 슬롯과 관계없는 숫자, 요일, 파일명은 기존 값을 바꾸지 않는다. |
| 의미 모호·필수값 누락 | '중요한 메일'의 기준 또는 계산식·결과 열 이름처럼 사용자가 선택해야 할 사항을 해당 슬롯의 질문으로 돌려준다. |
| 근거 없는 모델 후보 | 원문과 다른 요일, 보존 정책, 집계 임시 열 등을 확정하기 전에 대조한다. 지원하는 범위에서는 소유값과 실제 도구 계약으로 복원한다. |
| 모델 응답 형식 오류 | 확인 가능한 근거로 복구하는 경로를 먼저 적용한다. 일반 추출에서는 형식 오류를 제한적으로 재시도한다. 복구에 실패한 경우 내부 오류 종류를 trace에 남기고 생성·저장을 중단한다. |
| 연결·시스템·상태 오류 | Requirement의 시스템 오류 및 오래된 상태를 미정 업무와 구분한다. 실패한 경로의 이전 질문과 초안을 지운다. 선택적 요청 의미 해석의 오류는 진단에 기록한 뒤 기존 일반 설계 경로를 사용할 수 있다. |

두 측정 모두 로컬 Ollama, NVIDIA GeForce RTX 4060 Ti 8GB, 공개 `qwen3.5:9b` Q4_K_M을 사용했다. 가중치 SHA-256은 `02d45dc1cf451ba2475ac33b301c2dd8f985abe4c182ce04a1f2f5bf0260278d`이다. 모델 별칭, 모델 다이제스트, 양자화, Python 버전·패키지, GPU·드라이버, 평가 프로필의 설정값이 일치했다. 컨텍스트는 32,768, 출력 한도는 4,096, temperature는 0, seed는 42다. 새 측정 첫 probe에서 Ollama가 보고한 모델 GPU 점유량은 5,604,082,973바이트였다.

Ollama 버전은 0.40.15에서 0.40.16으로 바뀌었다. 새 하니스는 SDK의 HTTP 전송과 단계 전후 장부까지 기록한다. 응답 수는 probe와 사례를 분리하며, 서비스 지연은 코드 전용 경로와 검증·허용된 합성 실행을 포함한다. 따라서 전후 지연 차이에는 오케스트레이션, 서버 버전, 계측 및 호스트 부하의 영향이 함께 들어간다.

평가 하니스 manifest는 `b13dba529d7438fc8528e010f4afbc187240208b90a3ba44ecd6257b856f5fb3`이다. 양쪽 프로필 모두 Deep Agent 생성기, SVM56 추천 힌트, Capability·Condition·Requirement 강제 검증을 사용했다. 선택적 모델 Verifier는 꺼져 있고 코드 Validator는 활성 상태다.

### 중간 실측에서 발견해 보완한 실패

첫 빌드 `3f3907ba…58fc4d`에서 R01~R05를 실행했다. 그때의 원본에서 R04는 이미 확정된 first/error를 다시 묻지 않았지만, 요구사항 후보의 `deduplicate_and_export_json`이 별도 other 업무로 수용됐다. 올바른 policy와 JSON 저장 업무가 있어도 Validator는 중복 other의 실행을 검증할 수 없어 초안을 차단했다. R06 실행 중 이 진단 측정을 중단하고 5건의 종결 기록과 당시 활성 호출을 원형 그대로 보존했다. Windows에서 종료한 시점의 파일 상태는 `running`이다. 이후 최종 재측정은 다른 디렉터리에서 R01부터 시작하고, 이 5건 및 미완료 호출은 최종 코호트 통계에서 제외한다. 독립 35개는 첫 빌드에서 실행하지 않았다.

두 번째 빌드 `29ba2dd9…c0a06a`의 진단 원본에서 R04는 정상 READY, 질문 0개, 합성 실행 정답 일치를 확인했다. 그러나 R02에서는 첫 빌드와 글자까지 동일한 `filter_and_export` 응답을 받았는데도, 새 중복 검사기가 설명 속 `amount ≥ 20`을 해석하지 못해 정상 워크플로우를 차단했다. 두 번째 실행은 R04까지 완료한 뒤 R05 진행 중 중단했다. 두 진단 실행의 종결 사례와 미완료 호출을 최종 비교에 합산하지 않는다.

다음 빌드는 업무 설명에 나타난 단일 수치 조건을 열·비교연산자·값으로 해석해 확정된 술어와 대조했다. 추가 동작, 다른 경계, 다른 결과 형식 또는 모호한 다중 입력은 보존했다. 두 진단의 R02와 R04 후보·초안 네 조합이 모두 재생 검사를 통과했다. 앱 manifest `1a04b35271479988869862fa7acb8e03c67163fc86a347870620a529c001f689`로 52건 전부를 실제 평가한 뒤 독립 코호트 시작 전에 종료했다. 그 52건의 별도 채점은 전체 성공 30/52, 필요한 질문 27/32, 업무 충족 67/88, 확정 조건 충돌 5/151, 수용 업무 중복 5/69였다.

이 중간 빌드는 M04~M06에서 정확한 예약과 출력이 있는데도 '예약 작업 만들기'를 별도 업무로 남겼다. X03에서는 JSON 산출물이 하나였으나 원문에 없는 집계 열 이름 변경·열 선택이 생겨 올바른 생성 초안을 거절했다. 독립 입력이나 결과를 열기 전에 이 두 경로를 추가로 검증했다. 최종 릴리스는 과거 빌드의 사례를 재사용하지 않고 측정한다.

최종 릴리스 앱 manifest는 `9bf4e43f381bee62e859d7bb9cb9ef7200b086df4ce883d940bbe734f3030b85`다. M01의 경우 모호한 `execute` 후보를 병합하기 전에 최초 요청의 범위, 직전 질문과 연결된 수치 답변, 명시된 조건·출력과 후보 설명의 일치를 모두 요구한다. 메일 발송, 추가 집계, 검수와 같은 잔여 업무를 설명하지 못하면 일반 검증 경로에 남긴다. 최종 코드를 고정한 시점까지 독립 35건을 실행한 기록은 없었다.

### 기존 기능 회귀 검증

중간 빌드의 설계·조건·지원 판단 2,199건과 화면·API의 대화 재개, 승인, 저장, 예약 관련 57건이 통과했다. M07에서는 단일 입력 표의 수식 답변만 같은 계산 업무에 연결했다. 서로 다른 입력이라는 근거가 있으면 같은 수식도 보존했다. R04의 첫 실측 후보와 실제 초안을 다시 검증했을 때 policy와 export가 각각 실행 노드와 대응했고 Validator가 READY를 반환했다. 이 재생 검사는 Qwen 실측 성공 여부와 별개다.

최종 릴리스에서는 설계·조건·지원 판단 2,243건 모두 통과했다. 집계 결과에 대한 원문·후보 대조를 직전 52건의 Requirement 응답 32개에 적용했을 때 X03 한 응답만 교정됐다. 실제 X03 초안 재생에서 Validator와 승인 후 저장 게이트를 통과했다.

초기 백엔드 전체 JUnit에는 3,355개 항목이 기록됐다. 실패·정리 과정 오류를 사례 ID로 합치면 고유 65건이었다. 필요한 Windows 셸과 임시 폴더 권한, 테스트용 환경 설정, 저장소가 요구한 선택 패키지를 맞춰 65건을 모두 재실행했다. 63건은 통과했고 2건은 기준 커밋과 수정본에서 동일하게 실패했다. 하나는 이전 버전에서 부분 저장한 예약의 원본 복구, 다른 하나는 전체 도구 카탈로그 테스트의 Gmail `email.list/read_messages` fixture 누락이다. 이는 전체 스위트를 재실행해 얻은 단일 통과율이 아니다. Windows에서 실행되지 않은 플랫폼 전용 테스트가 있다.

## 독립 표현에서의 관찰

H07~H12에서는 임계값, 중복 키, 중복 정책, 계산 배율, 원본 문서, 메일 수신자 가운데 각 요청에 빠진 것만 물었다. 반면 즉시 생성이 정답인 H01~H06에서는 H04만 전체 성공했다. H04는 요청대로 열 이름을 바꾸고 합성 입력 5행의 값과 순서를 유지한 CSV를 반환했다.

H01의 초안은 `credit ≤ 0`과 CSV를 올바르게 구현했지만, 중복된 `export_csv_from_table` 업무가 남았다. H05는 메일 주소·제목·본문을 정확히 구성했어도 불투명한 업무 항목과 부적합한 초안 이름 때문에 실패했다. H02의 동률 정렬은 중복 제거로 해석됐다. H13~H16에서는 현지 자정 경계가 실제 Gmail 조회 인자에 반영되지 않거나 입증되지 않았다. H18의 뉴욕 현지 금요일 17:20 CSV 요청은 시간대에 대한 별도 설명이 붙은 형태라 예약 중복 방지 경로에서 완전히 처리하지 못했다.

독립 H19~H24에서는 필요한 질문을 한 뒤에도 답을 실행 인자로 채택하지 못한 사례가 있었다. H20은 ‘두 통만’으로 변경했는데도 실제 조회 한도가 100이었다. H21은 마지막 행 정책을 재질문했고 H24는 답을 받은 메일 주소를 다시 물었다. H23은 결과 열 이름을 반영해 합성 JSON 5행과 순서가 정답에 일치했다.

H28에서는 원본이 요구한 별도 CSV·JSON 다운로드 둘을 장부에 온전히 보존하지 못했다. H29에서는 필터와 중복 제거의 개별 슬롯을 맞췄지만 실행 도구의 처리 순서가 요구와 달랐다. H32는 Markdown 요약과 메일이라는 두 결과가 명시돼도 형식·수신자를 다시 물었다. 단일 산출물 병합 검사와 별개로, 누락된 두 번째 산출물과 단계 순서를 대화 끝까지 확인하는 검증이 남아 있다.

독립 복합군에서 H34는 실제로 빠진 기준 숫자와 합산 열을 질문했고, H35는 다른 두 자료를 좌·우 입력에 각각 연결해 내부 조인한 뒤 JSON으로 저장하도록 구성했다. H35는 사전 기준상 합성 실행 대상이 아니었다.

## 추가 sLLM 도입 판단

**현 단계에서는 추가 sLLM 도입을 보류한다.** 동일 공개 모델에서 장부의 소유권과 실행 검증을 바꾸어 대표 실패 7건을 복구했고 호출 수도 감소했다. 독립군에는 모델 후보와 실제 초안이 이미 정확한데 수용 장부가 이를 중복 업무로 남겨 차단한 사례가 있었고, 답변을 받고도 확정 상태를 미정으로 돌린 사례도 있었다. 다음 우선순위는 답변과 슬롯의 연결, 새 표현으로 생성된 업무의 근거·산출물 대조, 현지 날짜 경계와 실행 순서의 결정적 검증이다. 별도 모델의 기여는 이번 측정에서 시험하지 않았다. 위 계약을 적용한 뒤에도 남는 의미 해석 오류를 대상으로 호출 비용과 지연을 포함한 비교 실험에서 이득이 확인될 때 도입을 판단할 수 있다.
