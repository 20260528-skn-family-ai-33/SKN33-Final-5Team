# 두 9B 모델의 호출 설정과 상주 유지

`previous-pilot32k` 지원 판정과 `final664-pilot32k` 설계를 같은 Ollama에서
사용할 때 native `/api/chat`, OpenAI `/v1/chat/completions`, 워밍업은 아래
실행 설정을 공유한다. 온도·seed·출력 길이·스트리밍·스키마는 각 역할의 값을 유지한다.

| 항목 | 두 9B 정책 |
| --- | --- |
| 문맥 길이 | 32768. native 요청과 등록된 모델 설정 모두 일치해야 한다. |
| shift | false. 긴 생성에서 앞쪽 문맥을 버리는 방식으로 장애를 숨기지 않는다. |
| truncate | false. 입력 초과를 자동 자르기로 숨기지 않는다. |
| keep_alive | -1. 짧은 평가 요청이 상주 유지 시간을 5분으로 바꾸지 않는다. |
| 동시 적재 | 두 9B, 각 모델 1개 실행 슬롯. |
| 계산 스레드 | 모델당 4개 기본값. 호스트 전체 CPU 수를 자동 적용하지 않는다. |

다른 모델의 앱 기본값은 유지한다. 예를 들어 기존 4B native 문맥 기본값은 16384다.
두 9B를 선택했을 때만 native 기본값이 32768이며 명시적인 환경 설정도 읽는다.
전용 게이트웨이는 두 모델의 충돌하는 문맥·runner 옵션과 `shift:true`,
`truncate:true`를 400으로 거절한다. 입력·스키마·샘플링을 몰래 바꾸지 않는다.
다른 모델의 호출은 기존대로 전달하므로, 외부에서 제3 모델을 로딩하면 두 상주 슬롯
중 하나가 교체될 수 있다. 상주 검증은 다른 모델을 호출하지 않는 구간에서 수행한다.

## 원인과 수정 범위

2026-11-11 14:56:41 KST에 previous 로딩이 시작됐고 15:01:50에 내부 Ollama가
`timed out waiting for llama-server to start`로 실패했다. HTTP 500은 게이트웨이가
내부 응답을 전달한 결과였다. 같은 모델의 실행 로그에서 `--context-shift` 유무가
반복해서 바뀌었고, 재로딩마다 네트워크 디스크의 BF16 파일을 다시 읽었다.

Ollama 0.40.13은 shift를 실행 프로세스의 설정으로 비교한다. native는 false를
명시하지만 stock OpenAI 변환기는 이 필드를 전달하지 않아 기본값으로 돌아간다.
타임아웃을 늘리거나 모델 이름을 바꾸는 것으로 해결하지 않는다.

`build-ollama-shift.py`는 공식 0.40.13 소스에서 OpenAI 요청의 선택적 `shift`,
`truncate` 두 필드를 native 요청에 전달하는 부분만 추가한다. 생략한 요청의 기본
동작과 모델 계산 코드는 바꾸지 않는다. 소스 압축 파일 SHA-256과 Go 배포판 SHA-256을
검사하고 OpenAI 변환 테스트를 실행한다. GPU 라이브러리·llama-server·GGUF·등록 digest는
재빌드하거나 변경하지 않는다. 준비한 프런트엔드 버전은 `0.40.13-a4b-shift1`이다.

`serving_request_policy.py`는 두 공개 API에 정책을 적용하고, stock 실행 파일이
옵션을 다시 무시하지 않도록 게이트웨이 시작 시 정확한 수정본 버전을 확인한다.
앱도 두 모델에는 이 옵션을 명시하므로 코드와 운영 경계가 동일한 정책을 갖는다.
이 방식은 앱 내부의 OpenAI SDK·도구 호출·스트림 변환을 별도로 재구현하지 않는다.

## 시간 제한

- 앱: `A4B_MAIN_TIMEOUT_S`를 유지한다(코드 기본 180초, 현재 운영 300초).
- 공개 게이트웨이: 내부 응답 대기 600초. 외부 프록시 제한이 이보다 짧을 수 있다.
- Ollama 초기 로딩: 10분. 네트워크 디스크의 첫 로딩에만 여유를 둔다.
- 워밍업: 모델당 900초. 두 모델의 GPU 적재 검증 후에 공개 게이트웨이를 연다.

이 값들은 서로 다른 작업의 제한이다. 정상 요청은 워밍업이 끝난 모델을 사용하며,
타임아웃 증가를 재로딩 방지의 근거로 삼지 않는다.

## 적용과 되돌리기

1. Linux Pod에서 `python3 scripts/runpod/build-ollama-shift.py`를 실행한다.
   빌드 자체는 서비스나 실행 파일을 교체하지 않는다. `build.json`의 검사·해시를 확인한다.
2. 기존 Ollama 프런트엔드와 시작·워밍업·게이트웨이 파일을 같은 백업 디렉터리에 보관한다.
   수정된 프런트엔드를 기존 `ollama/bin/ollama` 위치에 원자적으로 교체하고,
   `serving_request_policy.py`, `final_model_profile.py`와 시작·준비 검사 파일을 함께 배포한다.
3. 요청을 정리한 뒤 시작 감독 프로세스에 TERM을 보내고 새 시작 스크립트를 실행한다.
   Pod 자체를 Stop하거나 GPU 할당을 해제하지 않는다. 네트워크 디스크의 실행 파일과
   스크립트는 다음 시작에도 유지된다. 전체 디스크 재구축 시에도 수정본 빌드가 필요하다.
4. AWS의 기존 `env-overrides`에서 주소·인증·모델 별칭·다른 설정을 보존한다.
   문맥 32768, previous 지원 판정, final664 설계, 검토 off와 기존 출력·온도·시간 제한을
   확인하고 PR의 앱 코드를 배포한다. 파일 소유자 root와 권한 600을 유지한다.
5. 아래 실검증을 실행한다. 실패 시 프런트엔드와 정책·시작 파일을 **같은 백업 세트로**
   복원한 뒤 서비스만 재시작한다. 모델 파일과 등록 영수증은 복원 대상이 아니다.

## 검증

`verify-resident-models.py --base-url <현재 공개 모델 주소> --output <결과 JSON>`를
Pod 안에서 실행한다. 인증은 기존 파일에서 읽고 출력하지 않는다.

각 요청마다 previous → final664 순서를 유지하며 native와 OpenAI 경로에서 일반 응답,
JSON 스키마, 스트리밍을 검사한다(총 12회). HTTP 200뿐 아니라 종료 표시·비어 있지 않은
출력·스키마 결과·응답 시간과 두 모델의 등록 digest/GPU 적재/32K 문맥을 확인한다.
각 요청 뒤 PID가 같아야 하며 전체 구간의 새 runner 시작·로딩 실패 로그가 0건이어야 한다.
실제 AWS 앱의 모델 팩토리와 native 호출기도 별도로 교대 검증한다.

합성 호출의 연결·상주 검증이며 v2 89개/팀 52개 평가의 품질 점수 재측정은 아니다.
