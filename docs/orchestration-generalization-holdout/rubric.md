# 일반화 평가 동결 기준

새 요청 30개와 합성 입력을 함께 동결했다. 저작자는 기존 평가 사례의 키·자료형과 등록 도구 계약을 확인했다. 기존 사례의 요청·정답 텍스트, 예측, 실패 번호와 변경 중인 서비스 구현은 열람하지 않았다. 이 묶음의 모델 호출과 실제 커넥터 실행은 0회다. 동결 시각 이전에 다른 담당자가 시작한 개발 또는 다른 평가와 시간상 선후를 주장하지 않는다.

## 실행과 비교

freeze.json의 suites에 고정한 순서로 동일한 cases.json에서 ID를 고른다. Fast는 6개, Focused는 Fast를 포함해 16개, Full은 30개이며 전체 명단은 동결 파일에 있다. 이는 사례 선택 규칙이다. 각 실행에는 실제 모델·카탈로그·서비스 커밋·설정 지문과 시간대, 요청별 응답·질문·워크플로·소요 시간을 기록한다. 하니스 계약에서는 runpod-rebuild 프로필과 freeze.json의 gold_sha256이 필요하다. 각 실행은 원본 corpus 전체를 먼저 검증한 뒤 사례를 선택한다. 개별 모드를 실행하지 않은 경우 결과는 미측정이다.

## 사례당 채점

1. 첫 응답과 최종 응답을 별도로 비교한다. 초기·최종 라우팅의 분모는 각 시점에 실제 시도한 전체 사례다. 시스템 오류는 기대 클래스의 미검출이다. 모든 미지원 필수 행동과 잠정 지원 단계를 구분해야 하며 필수 외부 행동을 생략한 부분 설계는 완결로 인정하지 않는다. 사용자가 직접 하겠다고 한 작업은 시스템의 의무에서 뺀다.
2. 명시 슬롯을 값 단위로 비교한다. 필수 질문은 지정된 누락 슬롯을 해소할 때 인정한다. 이미 알려진 슬롯 재질문과 관련 없는 질문은 각각 기록한다. 허용어는 답변 시뮬레이터의 문자열 매칭용이며 독립 판정에서는 동의어를 허용한다. 질문에 맞는 answer_policy만 제공한다. 연결이 불분명하거나 여러 답이 가능한 경우 임의 답변을 만들지 않는다. 답변·수정 이후에는 바뀐 슬롯과 유지해야 할 기존 슬롯 모두 검증한다.
3. 도구 이름이 맞아도 필요한 작업, 인자, 실제 자료 ID, 출력 포트와 소비 단계의 유향 경로를 별도로 검증한다. 수학적·기능적으로 동등한 구현은 근거와 대응 단계를 기록하고 의미 점수에 반영한다. 원시 도구 존재 점수와 분리한다. 두 결과를 요청한 사례는 각 출력을 독립적으로 열 수 있고 올바른 분기 데이터를 받는 경우에만 결과물 점수를 준다.
4. 표는 열 이름, 행 수, 전체 값, 자료형을 비교한다. sorted 결과는 명시한 정렬 키 순서, 원본 순서 보존은 실제 행 순서로 확인한다. 그룹 순서가 미지정된 사례는 중복을 포함한 행 다중집합으로 비교한다. 비표 결과는 정수·문자열·중간 결과에 해당하는 사례별 오라클로 확인한다. 로컬 실행을 지원하지 않는 초안은 의미 검토와 실행 성공을 구분해 기록한다.
5. 날짜는 지정한 IANA 시간대에서 0시부터 다음 날 0시까지의 반열린 구간이다. 각 사례에 고정된 두 epoch 경계와 경계 전후 네 메시지의 포함 여부를 대조한다. 수정 전후 날짜는 각각 검사한다. 가상 받은편지함에는 연결 여부 메타데이터만 주며 실제 이메일이나 API는 조회하지 않는다.
6. 같은 지표의 비교에는 동일한 사례·분모를 사용한다. 실행 성공은 하니스가 실제로 허용된 로컬 합성 행을 대조한 사례에만 표시한다. 실행 금지, 해당 없음, 근거 없음 및 미검토는 성공으로 집계하지 않는다. 미측정은 비율 분모와 함께 명시한다. 예상 행·골드·영역·분할·루브릭·평가 ID는 모델 입력으로 보내지 않는다.
