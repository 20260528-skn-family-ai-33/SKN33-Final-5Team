# A4B 실제 RunPod Qwen 기반 되묻기 및 워크플로우 생성 E2E 검증

## 1. 작업 목적

현재 A4B 프로젝트는 자연어 요청을 분석하고, 필요한 정보를 되물은 뒤, 도구를 선택하여 실행 가능한 워크플로우를 생성하는 서비스입니다.

기존 되묻기 시스템의 코드 제어 오류는 일부 수정되었으며, 합성 모델 응답 기반 회귀 테스트를 통과한 상태입니다.

하지만 아직 RunPod에서 서빙 중인 **실제 Qwen 모델의 자연어 이해, 되묻기 판단, 다중 턴 상태 관리, 워크플로우 생성 품질은 검증되지 않았습니다.**

이번 작업에서는 기존 검증 보고서인 `clarification-system-audit.md`와 관련 테스트 및 실제 소스 코드를 확인하여, 실제 Qwen을 연결한 E2E 평가를 수행하세요.

핵심 목표는 다음과 같습니다.

1. 실제 RunPod Qwen 모델이 사용자의 요청을 올바르게 이해하는지 검증
2. 필요한 경우에만 되묻기를 수행하는지 검증
3. 사용자가 이미 제공한 정보를 반복 질문하지 않는지 검증
4. 답변을 기존 대화 상태와 정확하게 병합하는지 검증
5. 최종 워크플로우가 사용자 요구사항을 충족하는지 검증
6. 생성된 워크플로우의 구조와 실제 실행 가능성을 검증
7. 실패 원인을 Qwen 모델, 프롬프트, 조건 검증, LangGraph 상태 관리, 도구 추천, Frontend/API 계층으로 분리
8. 재현된 오류를 수정하고 동일한 사례로 재평가

이번 작업은 추가 sLLM 도입이나 모델 파인튜닝을 전제로 하지 않습니다.

우선 기존 Qwen과 Orchestration Layer를 사용하여 실제 문제를 측정하고 개선하세요.

## 3. RunPod Qwen 연결 및 설정 확인

기존 모델 호출 방식을 먼저 확인하세요.

다음 항목을 점검하세요.

- `A4B_MAIN_PROVIDER`
- `A4B_MAIN_BASE_URL`
- 현재 사용 중인 Qwen 모델 ID
- Ollama 또는 vLLM 서빙 방식
- `/api/chat` 또는 OpenAI 호환 `/v1/chat/completions` 경로
- API 인증 필요 여부
- 모델의 최대 context length
- temperature, top_p, max_tokens 설정
- Thinking 모드 설정
- JSON schema 및 structured output 지원
- timeout, retry, concurrency 설정
- capability / condition / requirement 검사 MODE

**환경변수 이름과 기능은 실제 코드를 기준으로 확인하세요. 임의의 설정을 만들어 적용하지 마세요.**

현재 프로세스 환경, 개발 환경파일, 안전하게 조회 가능한 배포 설정에서 기존 연결 정보를 확인하되 API 키나 토큰을 출력하지 마세요.

기존 endpoint를 찾을 수 있다면 실제 모델 연결 및 간단한 구조화 출력 요청을 검증하세요.

연결 정보가 없거나 인증이 필요하면 임의의 외부 모델이나 GPT API로 대체하지 마세요.

그 경우에는 연결 불가 원인을 정확히 기록하고 실제 모델 검증이 필요한 항목을 분리하세요.

### 환경 설정 주의 사항

- 기존 `.env` 파일 덮어쓰기 금지
- API 키 출력 및 로그 저장 금지
- 기존 서비스 endpoint 변경 금지
- 운영용 모델 설정을 테스트 목적으로 영구 변경하지 않기
- 실제 모델과 mock 응답을 명확히 구분하기
- RunPod GPU 비용을 고려하여 불필요한 반복 호출 방지
- 테스트 대상이 실제로 Qwen인지 모델 ID와 응답 메타데이터로 확인

## 4. 실제 평가 데이터셋 구축

기존 10개 사례를 출발점으로 사용하되, 최소 50개 평가 시나리오를 구성하세요.

동일하거나 유사한 요청을 반복하는 것만으로 사례 수를 채우지 마세요.

다음 유형을 반드시 포함하세요.

| 유형 | 최소 사례 수 |
|---|---:|
| 명확한 요청 (READY) | 10 |
| 필수 정보 누락 (CLARIFY) | 10 |
| 상대 날짜·시간·수량 해석 | 8 |
| 다중 턴 답변 및 조건 변경 | 10 |
| 지원하지 않는 기능 (UNSUPPORTED) | 5 |
| 여러 업무가 포함된 복합 요청 | 7 |
| **합계** | **50** |

각 사례에 정답 데이터를 작성하세요.

정답에는 다음 항목을 포함해야 합니다.

- 사용자 요청
- 이전 대화 맥락
- 연결된 도구 및 리소스 상태
- 기대 의도
- 기대 추출 조건
- 필수 조건 누락 여부
- 기대 분류 결과
- 허용되는 되묻기 내용
- 질문하면 안 되는 조건
- 기대 도구 및 operation
- 기대 워크플로우 단계와 의존성
- 실행 가능 여부

정답은 실제 등록된 도구 카탈로그와 업무 정책을 기준으로 작성하세요.

개발자가 임의로 만들어낸 존재하지 않는 도구를 실제 지원 도구처럼 처리하지 마세요.

판정이 모호한 사례는 별도로 표시하고 정답을 확정하기 전 평가에서 제외하세요.

## 5. 반드시 검증할 대표 시나리오

### 사례 A — 수량 조건 이해

사용자:
"Gmail에서 최근 5개 메일을 요약 정리해줘."

기대:
- Gmail 소스 인식
- 최근 5개 조건 유지
- 불필요한 수량 재질문 금지
- 관련 도구와 operation 선택
- 연결된 Gmail 계정이 없으면 연결 필요 안내
- 연결 상태와 워크플로우 설계 가능 여부 구분

### 사례 B — 상대 날짜 해석

사용자:
"Gmail에서 어제 온 메일을 요약해줘."

기대:
- 사용자의 시간대와 요청 기준 시각으로 어제 날짜 범위 계산
- 날짜를 사용자에게 다시 질문하지 않음
- 다음 날 답변하더라도 원래 요청의 기준시각 유지

### 사례 C — 필수 정보 누락

사용자:
"매일 오전 9시에 매출 보고서를 이메일로 보내줘."

기대:
- 매일 09:00 추출
- 매출 데이터 소스 확인
- 수신자 정보 확인
- 누락된 필수 정보만 질문
- 이미 제공된 실행 시간 재질문 금지

### 사례 D — 이전 답변 반영

사용자:
"매출 데이터를 분석해서 이메일로 보내줘."

A4B:
"매출 데이터는 어디에서 가져오면 될까요?"

사용자:
"연결된 데이터베이스에서 가져와."

기대:
- 이전 요청과 현재 답변 병합
- 데이터 소스를 연결된 DB로 확정
- 데이터 소스를 다시 질문하지 않음
- 남은 조건에 대해서만 질문

### 사례 E — 사용자 조건 변경

사용자:
"최근 5개 메일을 요약해줘."

이후 사용자:
"아니, 10개로 바꿔줘."

기대:
- 최신 수량 10개 적용
- 이전 수량 5개 폐기
- 다른 확정 조건 유지
- 최종 워크플로우에 10개 반영

### 사례 F — 복합 요청

사용자:
"매일 오후 6시에 Gmail로 받은 고객 문의를 분석해서 중요 내용을 요약하고 Notion에 정리해줘."

기대:
- Gmail 수집
- 고객 문의 분석
- 요약
- Notion 저장
- 실행 시간 추출
- 작업 순서 및 데이터 의존성 반영
- 연결·권한 상태 확인
- 필요한 정보만 추가 질문

실제 도구 카탈로그에 해당 기능이 없다면 없는 기능을 만들어내지 말고 미지원 또는 수동 검토로 분류하세요.

## 6. 실제 Qwen 원본 출력 수집

테스트할 때 Frontend에 표시된 메시지만 수집하지 말고 내부 단계별 결과를 수집하세요.

각 테스트에서 다음 정보를 기록하세요.

1. 입력 요청
2. 기존 상태 요약
3. Qwen 호출 단계
4. 요청에 사용된 모델 ID
5. 실제 Qwen 원본 출력
6. 구조화 파싱 결과
7. 추출한 사용자 의도 및 조건
8. 사용한 도구 후보
9. Capability 결과
10. Condition 검증 결과
11. Requirement Ledger 상태
12. READY / CLARIFY / UNSUPPORTED 결정
13. 사용자에게 표시한 질문
14. 다음 대화 이후 변경된 상태
15. 생성된 워크플로우 JSON
16. Validation 결과
17. 소요 시간 및 토큰 사용량(제공되는 경우)

합성 테스트에서는 mock 출력으로 명시하고, 실제 Qwen 테스트에서는 live 출력으로 명시하세요.

모델 응답이나 추적 로그에 인증정보, 개인 메일 내용 또는 고객 정보가 포함되지 않도록 합성 데이터만 사용하고 저장 전에 민감정보를 제거하세요.

## 7. 다중 턴 되묻기 평가

이번 작업에서 가장 중요한 평가입니다.

단일 턴 요청만 테스트하지 마세요.

최소 10개 이상의 다중 턴 시나리오에서 실제로 다음 과정을 반복하세요.

사용자 요청
→ Qwen 조건 추출
→ CLARIFY
→ 사용자 답변
→ 상태 병합
→ 남은 조건 검증
→ 필요시 추가 질문
→ READY
→ 워크플로우 생성

실제 모델이 생성한 질문을 기준으로 다음 답변을 연결하세요.

각 시나리오마다 다음을 확인하세요.

- 동일 조건 반복 질문 여부
- 이전 답변 반영 여부
- 질문 ID 및 pending_questions 유지
- session_id / thread_id 유지
- 최신 조건 변경 반영
- 질문 종료 여부
- 잘못된 READY 전환
- 불필요한 질문 횟수
- 실제 사용자 요구와 최종 JSON의 일치 여부

체크포인트 복원을 위해 가능한 경우 동일 세션을 재시작하는 테스트도 포함하세요.

## 8. 워크플로우 생성 평가

되묻기 성공만으로 전체 성공이라고 판정하지 마세요.

READY 이후 실제 Qwen이 생성한 워크플로우를 평가하세요.

다음 항목을 구분하세요.

### 구조 유효성
- JSON 파싱 성공
- 필수 스키마 충족
- step ID 중복 없음
- tool ID 및 operation 유효
- 입력·출력 참조 유효

### 의미 정확성
- 사용자 요청의 모든 필수 업무 포함
- 불필요한 업무 추가 여부
- 올바른 도구 및 operation 선택
- 사용자 조건과 인자 일치
- 데이터 흐름 및 의존성 일치
- 기존 대화에서 수정한 조건 반영

### 실행 가능성
- 기존 검증기 통과
- 필요 시 재시도 및 repair 수행
- 실행 가능한 합성 도구에서 실제 실행
- 예상 결과와 실행 결과 비교

### 안전성
- 권한 없는 외부 발송 방지
- 승인 없는 실제 데이터 변경 방지
- 테스트용 이메일 실제 발송 금지
- 실제 Gmail, Notion 또는 고객 DB 접근 금지
- 미지원 도구의 임의 생성 방지

실제 외부 연동이 필요한 기능은 mock 또는 sandbox connector로 검증하고, 외부 서비스 실행 성공으로 기록하지 마세요.

## 9. 평가지표

최소 다음 지표를 계산하세요.

| 지표 | 정의 |
|---|---|
| Intent Accuracy | 사용자 의도 정확도 |
| Slot Extraction F1 | 조건 추출 정밀도·재현율 |
| Routing Macro F1 | READY/CLARIFY/UNSUPPORTED 분류 성능 |
| Necessary Question Recall | 필요한 질문을 수행한 비율 |
| Unnecessary Question Rate | 불필요한 질문 비율 |
| Repeated Question Rate | 이미 해결된 조건을 재질문한 비율 |
| Answer Incorporation Accuracy | 사용자 답변 반영 정확도 |
| Clarification Completion Rate | 되묻기 완료율 |
| Workflow Schema Validity | 스키마 검증 통과율 |
| Tool/Operation Accuracy | 도구·operation 선택 정확도 |
| Requirement Coverage | 사용자 요구사항 충족률 |
| Workflow Execution Success | 실행 결과가 기대 결과를 만족한 비율 |
| Latency p50/p95 | 실제 모델 포함 처리 지연 |

분모와 평가 대상 수를 모든 결과에 명시하세요.

분류 정답, 질문 필요성, 슬롯 및 workflow 정답은 평가 전에 고정하세요.

평가에 실패한 사례를 사후에 정답 수정으로 통과 처리하지 마세요.

복합 요청은 작업별 부분 점수와 전체 요청 성공 여부를 구분하세요.

## 10. 오류 분석 및 수정

실패 사례를 원인별로 분류하세요.

- Qwen 자연어 의미 추출 실패
- Qwen 구조화 출력 실패
- Capability 판단 실패
- Condition 검증 실패
- Requirement Ledger 누락·충돌
- LangGraph 상태 복원 문제
- 질문 생성 문제
- 이전 답변 반영 실패
- 도구 추천 ML 오류
- 워크플로우 생성 오류
- Validator/Executor 오류
- Frontend/API 메시지 전달 문제
- 모델 서버 timeout 또는 오류

**원인을 확인하지 않고 Qwen 프롬프트만 반복 수정하지 마세요.**

확인된 문제에 대해서는 최소 범위의 수정안을 적용하세요.

기존 코드를 수정할 때에는 다음을 지키세요.

- 정상 동작하는 기존 기능 보존
- 기존 모델·서빙 경로 유지
- 별도 sLLM 도입 보류
- 기능 변경 전 실패 테스트 작성
- 변경 후 동일 사례 재평가
- 기존 회귀 테스트 실행
- 기능별 변경 이력과 원인 기록

모델 호출 실패를 정상적인 CLARIFY로 처리하거나 임의의 성공 결과로 대체하지 마세요.

## 11. 평가 및 재평가 절차

다음 순서를 지키세요.

**Phase 1 — 환경 점검**

RunPod endpoint, 실제 모델 ID, provider, 테스트 MODE, 코드 revision 확인

**Phase 2 — Baseline 측정**

현재 소스를 수정하지 않은 상태에서 실제 Qwen으로 평가 수행

**Phase 3 — 오류 분석**

실패 사례와 원본 응답을 바탕으로 실패 원인 분류

**Phase 4 — 최소 수정**

재현된 문제만 수정하고 수정 내역 기록

**Phase 5 — 동일 코퍼스 재평가**

Baseline과 같은 입력, 시간 기준, 도구 상태, 모델 설정으로 비교

**Phase 6 — 회귀 검증**

기존 Python 및 TypeScript 테스트와 주요 워크플로우 검증 실행

가능하면 평가용 사례와 수정에 사용하는 개발용 사례를 분리하여, 수정 과정에서 특정 문장에만 과적합되지 않도록 하세요.

동일 조건에서 여러 차례 실행해 모델 출력 변동성을 별도로 확인하세요. API 호출량은 합리적인 범위에서 제한하세요.

## 13. 최종 작업 원칙

이번 작업에서 가장 중요한 것은 **실제 Qwen이 얼마나 정확하게 사용자 요청을 이해하고, 필요한 조건을 되물으며, 실행 가능한 워크플로우를 생성하는지 정량적으로 검증하는 것**입니다.

기존 합성 테스트가 통과했다는 이유로 실제 모델의 품질이 검증됐다고 판단하지 마세요.

가능한 작업은 실제로 수행하고, 접근 권한이나 환경 문제로 수행하지 못한 항목은 그 이유와 재현 가능한 명령을 남기세요.

실제 모델 검증 결과를 바탕으로 구조 개선이 필요한지, 프롬프트 개선이 필요한지, 별도의 소형 모델이 필요한지 판단하세요.
