# 로컬 공개 Qwen3.5 9B 의미 판정 기준과 지표 범위

작성 기준: 2026-11-10, Asia/Seoul. 이 문서는 평가 준비 및 계측 기준이며 실제 모델 평가 결과가 아니다. 기존 RunPod 결과, 고정 gold, 애플리케이션 소스를 변경하지 않는다. 로컬 공개 모델 결과는 RunPod custom 모델 결과와 합치지 않는다.

고정 gold: `qwen-live-evaluation-cases.json`, canonical SHA256 `e939c051a940915c4061b45221e7f1353b8ce2157677d379ae193de13b1300da`. 이 hash는 `gold_sha256` 필드를 제외한 JSON을 기존 `digest()`로 계산한 값이며 파일 바이트 SHA256과 다르다.

## 1. 고정 코퍼스의 기회 수

아래 수는 전체 코퍼스를 모두 검토했을 때의 정답 범위다. 실제 live 지표의 분모는 호출 여부, 실행 여부, 검토 여부에 따라 달라지므로 각 지표에 포함·제외 사례 수를 함께 보고한다.

| 항목 | 전체 | development | holdout |
|---|---:|---:|---:|
| 사례 | 52 | 37 | 15 |
| 초기 READY / CLARIFY / UNSUPPORTED | 25 / 21 / 6 | 17 / 15 / 5 | 8 / 6 / 1 |
| 초기 정답 슬롯 수 | 120 | 85 | 35 |
| 필수 누락 슬롯 수 | 32 | 23 | 9 |
| 실제 질문·답변을 요구하는 다중 턴 사례 | 10 | 7 | 3 |
| 후속 답변으로 추가·변경되는 정답 슬롯 수 | 14 | 10 | 4 |
| 최종 READY 대상 필수 업무 수 | 88 | 60 | 28 |

- 전체 gold workflow 업무는 **104개**다. 기존 scorer의 Tool/Operation Accuracy와 Requirement Coverage는 `final_routing == READY`인 사례의 **88개 업무**만 대상으로 한다. 104개 전체 업무를 평가한 수치로 설명하지 않는다.
- 초기 슬롯 120개는 정답 슬롯의 수다. Slot Extraction F1의 실제 분모는 `2TP + FP + FN`이다. 누락은 FN, 틀린 값은 FP와 FN, 명시적으로 검토한 근거 없는 추가 값은 FP로 센다.
- 후속 슬롯 14개는 10개 clarification 사례와 M11/M12 수정 사례를 포함한다. 기존 Answer Incorporation Accuracy는 실제 후속 턴이 기록된 사례만 평가한다. 답변 단계까지 못 간 사례 수와 제외된 기회 수를 별도로 보고한다.
- 합성 로컬 실행 대상은 R02/R03/R04/R05/M01/X02, 6개다. 외부 연동 미실행 대상은 16개, 실행 예정 없는 대상은 30개다. 실행 성공률 분모는 실제 실행된 수이며, 실행 전 단계에서 실패한 대상도 별도 건수로 남긴다.

## 2. live, 코드 recipe, 미실행, 미검토 구분

기존 `metrics()`는 `status in (completed, failed)`이면서 `live_model_calls > 0`인 사례를 live 지표 대상으로 삼는다. `completed`는 측정 종료이며 정답 성공을 뜻하지 않는다. `failed`도 live 호출이 있으면 routing 등의 실패 평가에 포함된다.

R01/T08은 이전 RunPod 기록에서 모델 호출 0회의 코드 recipe였다. 로컬에서는 실제 기록으로 다시 구분하며, 이 두 개가 항상 코드 전용이라고 미리 집계하지 않는다. `all_backend_metrics_including_code_recipes`는 코드 recipe를 포함한 서비스 전체 지표이고 모델 자체 품질 지표가 아니다. 코드를 통과한 사례를 모델 호출 사례로 바꾸어 raw 결과에 기록하지 않는다.

`not_run`과 `running` 사례는 성공으로 세지 않는다. 부분 실행에는 요청 52개, 측정 종료 수, 실제 호출 사례 수, 코드 전용 수, 미실행 수, 중단 중인 사례를 함께 적는다. 진행 중 호출의 최종 응답·토큰·지연은 추정하지 않는다.

의미 라벨이 없는 사례는 미검토다. 누락 라벨을 성공이나 정확도 0으로 채우지 않는다. 실제 호출을 했지만 미검토인 사례와 호출 자체가 없는 사례를 구별한다. 이 문서 작성은 로컬 baseline의 의미 판정을 수행한 것으로 집계하지 않는다.

## 3. 독립 의미 검토 방법

1. 원문, 이전 대화, 고정 시각·시간대, 합성 자료·연결 metadata, gold를 먼저 읽는다. 결과에 맞춰 gold를 바꾸지 않는다.
2. 원본 모델 응답, 단계별 수용 상태, 최종 workflow를 구분한다. 원본 모델이 제안했지만 validator가 거절한 값과 시스템이 실제 확정한 값은 다르다. 최종 planner가 업무를 복구했더라도 중간 requirement 추출 누락은 근거에 남긴다.
3. `observed_slots`는 첫 사용자 턴 종료 시 수용된 상태를 기준으로 기록한다. `final_observed_slots`는 답변·수정 이후 상태다. 모델 단계의 원문 추출 품질은 별도 설명 없이 이 서비스 전체 슬롯 점수와 동일시하지 않는다.
4. 질문은 실제 표시 순서대로 라벨링한다. 미답변 질문의 재노출과 이미 해결된 조건의 재질문을 구별한다. 질문 하나가 여러 필수 슬롯을 묻는 경우 실제 질문 내용에 근거해 슬롯들을 연결한다. C07/C08의 hour는 완전한 시각 질문이며 분만 묻는 것을 시각 전체 확인으로 보지 않는다.
5. `task_coverage`는 등록 도구 존재뿐 아니라 실제 인자, 자료 출처, 입출력 참조, 순서와 의존성까지 만족해야 true다. gold가 허용하는 filter/sort 공용 노드와 선택적 finish는 허용하되, 해당 설정이 실제로 들어 있는지 확인한다.
6. 다중 턴에서는 같은 session/thread, 질문 ID, 대화 이력, revision, 최신 답변 반영과 기존 조건 보존을 확인한다. M11은 5→10 변경, M12는 다음날 답변에도 원래 날짜 유지가 필요하다.
7. 날짜는 고정 시각·시간대와 실제 Gmail query의 절대 경계를 대조한다. T05/T06의 경계 길이는 각각 23/25시간이다. metadata·query 검증을 실제 Gmail 조회 성공으로 기록하지 않는다.
8. 요구된 업무가 모두 있어도 근거 없는 업무나 발송·변경이 추가되면 전체 요청 성공으로 인정하지 않는다. 추가 업무를 단순 슬롯 정확도나 도구 존재 점수로 감추지 않는다.

기존 `compare-qwen-live-evidence.py`는 raw 모델 출력과 ledger 근거 필드 일부를 비교에서 제외한다. 해당 근거에 의존한 intent·환각 판정은 자동 재사용하지 않는다. 공개 로컬 모델의 baseline은 새로 검토하고, after의 라벨 재사용도 실제 판정 근거가 동일함을 별도로 확인한다.

## 4. 최종 사례 유효성과 후보 schema 지표의 구분

기존 JSON key `workflow_schema_validity`는 현재 코드에서 **최종 사례의 초안·서비스 검증 통과율**에 가깝다. 분모는 live 측정 사례 중 `schema_valid`가 bool로 기록된 사례 수, 분자는 true인 사례 수다. READY 및 서비스 issues 조건을 함께 사용하므로 순수 JSON schema 검사와도 같지 않다.

이 값은 모든 planner 생성 후보와 repair 후보를 분모로 하는 schema 통과율이 아니다. 이전 RunPod R10에는 실제 planner 후보 2개가 있지만 처리 예외로 최종 `schema_valid=null`이어서 기존 집계에서 누락된다. 생성 전 종료된 null과 실제 잘못된 후보가 나온 뒤 예외가 난 null을 같은 의미로 취급하지 않는다.

이번 범위에서는 후보 단위 계측을 대규모로 변경하지 않는다. 최종 보고에는 다음을 구분한다.

- 최종 사례 초안·서비스 검증 통과: `true / bool 기록 사례`, null 수를 함께 표시.
- 전체 대상의 올바른 최종 workflow 도달: 의미 검토까지 통과한 사례 수와 별도 분모.
- 원본 후보별 JSON/schema/validator 통과율: 별도 검토·계측 전에는 미측정이라고 표시. raw 후보가 확인된 파싱/변환 예외는 실패 분석에 명시.

## 5. 수식 비교 검토 정정 및 현재 동작 검증

초기 읽기 리뷰에서 clarification 완료 판정이 수식 공백을 정규화하지 않는다고 보고했으나, 실제 당시 출력과 현재 소스를 재확인한 결과 완료 판정도 이미 `same()`을 사용하고 있었다. 이는 리뷰의 오독이며 소스 결함 재현이나 수정 성과로 기록하지 않는다. `adjudicate-qwen-live.py`는 이 작업에서 변경하지 않았다.

추가한 `Backend/tests/design/test_qwen_live_adjudication.py`는 현재 동작 보존 검사다. 합성 라벨로 `qty * 2`, `qty*2` 및 공백 변형이 같은 수식으로 평가되는지, 잘못된 배수나 다른 결과 열 이름은 실패하는지 확인한다. 이 검사를 실제 Qwen 결과나 수정 전 실패 테스트로 표시하지 않는다.

검증: 새 scorer 검사 6개와 기존 평가기 검사 12개, **18 passed**. 기록은 `qwen-local-adjudication-tests-20261110.xml`이며 새 전용 basetemp를 사용했다. 실제 네트워크·모델 호출을 포함하지 않는 합성 검사다.

## 6. 추가 업무와 전체 성공의 optional 라벨 제안 — 미구현

현재 scorer의 task coverage는 요청한 업무의 충족률이다. 요청한 업무가 모두 존재하면서 불필요한 업무까지 추가된 경우를 독립적으로 벌점 주는 필드는 없다. gold를 바꾸지 않고 검토 라벨에 다음 정보를 추가하는 방법을 제안하며, 이 문서만으로 구현하거나 기존 라벨을 자동 변환하지 않는다.

| 제안 필드 | 값 | 의미 |
|---|---|---|
| `extra_unrequested_actions` | 미기재 또는 null | 추가 업무 여부를 아직 검토하지 않음 |
| `extra_unrequested_actions` | 빈 배열 | 추가 업무가 없음을 명시적으로 검토함 |
| `extra_unrequested_actions` | `{node_id, action, evidence}` 목록 | 원문에 근거 없는 추가 업무와 근거 |
| `whole_request_success` | 미기재 또는 null | 전체 요청 성공을 아직 검토하지 않음 |
| `whole_request_success` | true 또는 false | 별도 근거를 갖춘 명시적 전체 판정 |

`whole_request_success=true`는 자동 기본값으로 만들지 않는다. READY 대상에서는 추가 업무가 없다는 명시적 검토, 올바른 최종 route, 모든 필수 업무·인자·의존성·시간·이전 조건 보존을 확인해야 한다. CLARIFY/UNSUPPORTED 대상은 기대 분류와 질문·미지원 근거를 충족했는지 판정하며 불필요한 workflow 생성 자체를 성공 요건으로 삼지 않는다. 외부 연동의 실제 실행 여부는 이 필드와 별개다.

구현한다면 미검토/null은 분모에서 제외하되 미검토 수를 필수로 함께 보고하고, true와 추가 업무 목록이 동시에 존재하는 모순 라벨은 거절해야 한다. 기존 부분 점수와 새 전체 요청 점수를 따로 출력해 과거 결과의 의미를 바꾸지 않는다.
