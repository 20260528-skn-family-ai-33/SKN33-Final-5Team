# 도구·operation·ID 대응과 백엔드 추가 점검

이 문서는 PR #27의 최초 수정 이후 추가로 확인한 내용이다. 처음 기록할 때 추가 수정은 로컬에만 있었으며, 이후 PR27 통합 갱신에 포함했다. 아래 수치와 서버 상태는 각 절의 확인 시점에 해당한다. 현재 범위·활성화 설정·남은 확인은 [통합 현황](backend-pr27-progress-20261104.md)과 [통합 검증 요약](backend-pr27-update-evidence-20261104.json)을 기준으로 읽는다.

## 1. 문제가 있던 부분

모델의 56개 ID와 서비스 등록 ID는 현재 모두 대응한다. 서비스에는 제어·호환 항목 6개를 포함해 62개 ID가 있다. 이 가운데 기본 실행 경로가 22개이고, 업무 도구의 확장 operation은 88개다. **같은 ID가 등록됐다고 기본 설정과 모든 operation의 인자·출력까지 같다는 뜻은 아니다.**

| 추가로 재현한 문제 | 수정 내용 |
| --- | --- |
| 기본 동작에 arguments_json을 넣거나 확장 operation에 기본 설정을 넣어도 무시된 채 저장됨 | 노드 저장·초안 검증·실행에서 같은 계약 검사를 적용. 무시될 설정은 오류로 반환 |
| 표 읽기가 실제로 소비하지 않는 file_id 연결 포트를 안내함 | 파일은 settings.file_ids로 고르고 표 읽기의 연결 입력은 비우도록 카탈로그 수정 |
| 결과 저장이 소비하지 않는 documents 입력을 안내함 | 실제 사용하는 records/text/answer만 입력으로 안내 |
| records와 text를 함께 저장하도록 연결하면 text가 조용히 빠짐 | 본문이 둘이면 저장 노드를 분리하도록 검증·실행에서 차단. records+answer의 사용자 확인 저장은 유지 |
| 표 저장에 Markdown을 지정해도 저장 검증 통과 후 실행 실패 | write_result의 CSV/JSON 형식을 저장 전에 확인 |
| 확장 필터에 기본 필터의 field/operator/gte 규격을 넣어도 저장됨 | predicates의 column/op/ge·le 규격, 상수/열 비교 구분과 combine 값을 검사하고 생성 스키마에 반영 |
| 확장 필터의 실행 로그를 기본 execution_plan으로 덮어씀 | 성공·실패 로그 모두 실제 선택한 operation과 인자를 기록 |
| 재사용 목록이 확장 합계 노드의 출력 열을 기본 count로 잘못 안내 | 기본 설정으로 확장 출력 열을 추측하지 않고, 모르는 열은 명시적으로 미확인 처리 |
| finish 뒤의 작업도 연결·실행 가능 | 종료 뒤에 작업이 있는 초안을 저장·실행 전에 차단 |
| API의 모델 필요 여부 판정이 Python 실행기와 다름 | operation 카탈로그로 판정. 22개 기본 경로+88개 확장 경로를 양쪽 구현으로 대조 |
| operation 인자 계약이 바뀌어도 전달 규격 fingerprint가 같음 | 기본 설정 키와 operation 계약의 해시도 버전 판정에 포함. 기존 규격 예시는 백업 후 재출력 |
| 지원 재검토 지시에 여전히 '표 join은 미지원으로 유지'가 남음 | 등록된 join_tables 계약을 대조하도록 지시 수정. 미지원 결과를 코드로 억지로 지원으로 바꾸지는 않음 |

write_result와 export_result를 같은 이름의 도구처럼 바꾸지 않았다. 기본 write_result는 table을 저장하고, 기본 export_result는 records 또는 text/answer를 저장한다. export_result의 확장 serialize/write_json/write_csv는 각각의 operation 인자를 쓴다. 모델 점수도 확률로 변환하지 않았다.

## 2. 해결한 내용과 검증

- 고정 모델 카탈로그 56개 ID의 순서·서비스 등록 여부 대조: 미등록 0개.
- 기존 도구별 대표 실행 56건에 추가 동작 32건을 보완해 88개 operation의 계약·출력 경로를 검사했다. 파일 동작은 로컬 합성 fixture를 사용하고 모델·외부 연결은 주입된 대체 응답을 사용했다. 88개 모두를 실제 Qwen이나 Google 계정으로 검증했다는 뜻은 아니다.
- Python 전체: **1,620 통과, 2 건너뜀, subtest 4 통과**. 마지막 지원 재검토 지시 수정 후 관련 **441 통과**.
- Node API/UI: **752 통과, 1 건너뜀, 1 시간 초과 취소**. 기존 S3 보관 실패 처리 검사가 병렬 실행의 15초 제한에 걸렸으며, 코드 변경 없는 단독 재실행은 통과했다. 전체 한 번의 실행이 모두 통과했다고 표현하지 않는다.
- 타입 검사·빌드 통과. Node와 Python의 모델 필요 여부 **110개 경로 일치**.
- 이전에 실제 Qwen이 생성·저장한 한 표/두 표 흐름을 수정한 백엔드에서 그대로 다시 실행했다. 결과 B=40/A=30과 A=40/B=10이 기존 정답 및 저장 파일과 일치했다. 이 재실행은 새 모델 호출이 아니다.
- 원래 모델·데이터·기존 검증 결과는 유지했다. ML 학습이나 새 ML 평가 데이터 생성은 하지 않았다.

## 3. 미해결 사항

- 추가 수정본의 **새로운 Qwen 생성**은 아직 재확인하지 못했다. 기존 hvpj1j0mjrnsc3 주소의 모델 API는 404, 사용자가 제공한 최신 로컬 가이드의 pr0yhyflm3w9ur 주소는 401을 반환했다. 새 게이트웨이 인증을 연결한 뒤 재확인해야 한다. GPU와 서버 설정은 변경하지 않았다.
- Qwen이 요청하지 않은 조건을 추가하는 의미 오류는 계약 검증만으로 모두 막을 수 없다. 독립 검증기와 복합 요청의 반복 확인은 별도로 남아 있다.
- 공개 서비스 배포 후 로그인·파일 첨부·생성·저장·실행·다운로드를 확인해야 한다. 현재 검증은 로컬 격리 저장소를 사용했다.
- 모델 파일은 Git에 포함되지 않는다. 이 검증용 checkout의 기본 runtime/ml-bundle은 비어 있으므로 실제 추천 검증은 기존 팀 패키지 경로를 명시했다. 배포 서버의 모델 번들·해시·환경 설정은 별도 확인 대상이며, 이 로컬 상태만으로 운영 모델이 누락됐다고 단정하지 않는다.
- 검수 도구의 학습 사례 부족, AI 참고 라벨의 정확도, 실제 Google 연결은 이번 백엔드 수정으로 해결한 항목이 아니다.
- 첨부 로컬 가이드의 SQLite→RDS 전환 프롬프트는 참고 자료로만 읽었으며 해당 작업이나 운영 DB 접속은 실행하지 않았다. 가이드에 있는 인증정보도 코드·문서에 복사하지 않았다.

## 4. 후속 작업: 요청한 업무의 부분 누락 검사

### 문제가 있던 부분

- 도구·포트가 유효해도 계산·선별·정렬 중 일부를 빼먹을 수 있었다. 읽기만 남긴 초안의 차단 규칙으로는 이를 확인할 수 없었다.
- 생성기의 요구사항 설명은 실행 설정과 별개였다. 잘못된 초안을 검증 모델이 pass로 판단한 실제 사례도 있었다.

### 해결한 내용

- 생성 전에 별도의 Qwen 호출로 사용자 대화의 업무 목록을 추출한다. 현재 초안과 ML 점수는 이 추출기에 제공하지 않는다. 업무 ID·사용자 발화 인용·순차 의존 관계는 코드가 부여한다.
- 계산식·결과 열, 필터 값·경계, 정렬 순서·자료형, 그룹 집계, 결합 방향·키·정책, 출력 형식을 실제 노드 설정과 대조한다. 처리 결과가 최종 저장 노드의 입력으로 이어지는지도 검사한다.
- 자동 수정 중에는 요청·자료·카탈로그 해시와 업무 목록 해시를 유지한다. 저장 시 다시 검사하므로 모델 pass나 사용자 확인으로 누락을 덮어쓸 수 없다.
- `A4B_REQUIREMENT_MODE=enforce`로 활성화한다. 코드 기본값은 기존 배포 호환을 위해 off이며 `.env.example`에는 활성화 값을 추가했다. 켠 상태로 진행한 대화는 검증 의무를 유지한다.
- 생성 규격 실험은 `A4B_REQUIREMENT_GENERATION_MODE=bounded`로 분리했다. 기본값과 현재 로컬 설정은 baseline이다. bounded는 필수 번호 단계·요청 상수·최대 8192 출력 토큰을 사용하는 후보이며 최종 실제 실행 검증이 필요하다.
- 최종 로컬 회귀 검사는 1665 passed, 2 skipped, 4 subtests passed였다. TypeScript·실행 도구 구현·학습 모델·ML 평가 수치는 이번 변경으로 교체하지 않았다.
- 초기 검증 반복에서는 실제 Qwen의 한 표 계산→선별→정렬→JSON 저장·실행이 성공했다. 요청 업무 6개를 대조했고, 실제 생성 그래프에서 일부 처리를 제거하거나 연결을 우회한 대조 사례 5개를 모두 차단했다. 저장 JSON을 다시 읽어 실행 행과 일치하는 것도 확인했다. 이는 그 반복의 결과이며 이후 변경한 생성 규격 전체의 인증은 아니다.

### 미해결 사항

- 두 표 결합→계산→집계→정렬→저장의 최종 실제 실행은 아직 성공으로 확인하지 못했다. 누락·잘못된 결합 조건은 차단됐으며, 번호 규격 및 출력 길이 조정 과정의 실패 기록도 보존했다.
- 앞 절의 401 연결 문제는 인증 후 해소되어 실제 Qwen 호출을 수행했다. 이후 같은 pr0yhyflm3w9ur 주소의 `/v1/models`, `/api/tags`가 모두 HTTP 404로 바뀌어 최종 재실행이 중단됐다. GPU 중지·재시작·설정 변경은 하지 않았다.
- 단일 처리 경로의 명시적 표 작업을 우선 검증한다. 자유 서술 작업, 분기, 복수 결과 파일, 아직 대응하지 않은 operation은 자동 통과시키지 않는다. AI가 추출한 업무 목록 자체의 의미 정확도·완전성도 별도 한계다.
- 기존 배포본 검증기의 계산 후 파생 열 경고는 남아 있다. 그 패키지는 보존하고 기존 shadow 설정을 유지했다. 새 요청 업무 검사는 이 모델의 pass에 의존하지 않는다.
- 로컬 웹 프로세스는 재시작하지 않았고 팀 서비스 배포·PR 갱신도 하지 않았다. 실제 서버 연결 복구 후 최종 후보로 생성·저장·실행을 다시 확인해야 한다.
- 상세 기록은 로컬 `팀설정_복합흐름검증_20261103/task_omission_followup/PARTIAL_COVERAGE_WORK_RECORD.json` 및 원시 RESULT.json, CPU JUnit에 있다. 업무 시나리오·ML 최종 평가의 성공률로 환산하지 않는다.
