# PR27 통합 수정 현황과 확인 순서

작성일: 2026-11-04 (한국시간). PR27의 최초 수정과 이후 로컬 수정사항을 함께 설명한다. 모델 가중치와 학습 데이터는 바꾸지 않았다.

## 1. 문제가 있던 부분

ML이 도구 후보를 제시한 뒤에도 생성기·저장 검사·실행기가 서로 다른 설정과 입력을 기대했다. 따라서 올바른 도구를 골라도 두 파일을 읽지 못하거나, 결합한 표의 집계·정렬이 실패할 수 있었다. 실행 상태가 성공이어도 Qwen이 임의 필터를 추가해 결과를 모두 지우거나 요청한 처리 일부를 빠뜨리는 사례도 있었다.

## 2. 해결한 내용

### 최초 PR27에 있던 수정

- 생성기에 기본 도구 설정과 확장 operation의 실제 인자·포트를 구분해 제공한다.
- 실행 전 파일 검사와 실제 파일 읽기가 같은 선택 함수를 사용한다. 서로 다른 원본을 동일한 실행 파일로 잘못 연결하면 읽기 전에 차단한다.
- 결합 등으로 만든 표에 단일 원본 file_id가 없어도 집계·정렬할 수 있게 한다.
- 원본 파일 operation과 하위 워크플로 입력을 각각의 실행 계약에 맞게 검사한다.
- 응답 계약 오류를 제한된 수정 재시도 안에서 처리한다.

### 이번에 같은 PR에 추가하는 수정

- 기본 설정과 확장 operation 인자를 섞어 넣어도 조용히 무시되지 않게 한다. 생성 검증·노드 저장·실행에서 계약을 확인한다.
- 표 읽기·결과 저장 포트를 실제 실행 코드에 맞춘다. 저장 본문 일부가 사라지는 연결, 잘못된 출력 형식, 종료 뒤 작업을 차단한다.
- 확장 필터의 인자 규격과 실제 operation 로그를 맞춘다. 재사용 도구의 출력 열을 모르면 확인되지 않은 것으로 표시한다.
- API와 Python의 모델 호출 필요 여부를 같은 카탈로그로 맞춘다. 22개 기본 경로와 88개 확장 operation, 총 110개 경로를 대조했다. 모델의 56개 ID 중 미등록 ID는 0개다. ID 대응은 모든 외부 계정·실행 환경의 준비 완료를 뜻하지 않는다.
- 생성 전에 사용자 요청만으로 업무 목록을 별도 추출한다. 기존 초안이나 ML 점수는 이 추출기에 주지 않는다.
- 계산식·열·선별 경계·정렬·집계·결합 정책·출력 형식을 실제 노드 설정과 대조하고, 처리 결과가 최종 저장까지 연결되는지 확인한다. 요청·자료·카탈로그 또는 업무 목록이 바뀌면 저장 전에 다시 검사한다.
- 모델의 통과 판정이나 사용자 확인만으로 업무 누락을 덮어쓸 수 없게 한다. 읽기·저장만 남기는 축소 초안도 확인한다.
- 검증 모델로 보낼 때 불필요한 null 설정을 복사본에서 제거한다. 원래 초안과 고정 검증 패키지는 유지한다.

### 활성화 설정과 적용 범위

| 설정 | 기본값과 동작 |
| --- | --- |
| `A4B_REQUIREMENT_MODE` | 코드 기본값 `off`. `enforce`는 요청 업무 추출과 저장 전 대조를 활성화한다. `.env.example`은 활성화 예시이며, 팀 배포 환경을 자동 변경하지 않는다. |
| `A4B_REQUIREMENT_GENERATION_MODE` | 기본값 `baseline`. 기존 생성 방식을 유지한다. `bounded`는 번호별 필수 단계와 요청 상수, 출력 길이를 제한하는 실험 후보이며 기본 활성화하지 않는다. |
| `A4B_VERIFIER_MODE` | 이번 수정에서 팀 배포 설정을 강제로 바꾸지 않는다. 후속 로컬 확인은 `shadow`였다. 파생 열 오판이 남아 있어 기존 검증기의 강제 차단 전환은 별도 확인 대상이다. |

업무 추출은 추가 모델 호출이 필요하고, 추출 자체의 의미 오류 가능성이 있다. 현재 업무 대조는 명시적인 단일 경로의 표 작업을 우선 지원한다. 분기·복수 결과 파일·자유 서술 등 확인되지 않는 작업은 자동 통과시키지 않는다. 대응하지 않은 operation도 지원 완료로 간주하지 않는다.

### 검증 결과를 읽는 방법

| 확인 시점 | 확인한 사실 | 해석 범위 |
| --- | --- | --- |
| 최초 PR27 | 실제 팀 Qwen과 SVM56 힌트, 로컬 서비스 핸들러로 한 표 및 두 표의 생성·저장·실행 성공. 저장 파일도 예상 행과 일치 | 당시 코드의 각 1회 사례. 이후 추가 수정본의 성공으로 옮겨 적지 않는다. |
| 도구 계약 추가 수정 | 56개 도구 대표 동작과 총 88개 확장 operation 계약·출력 경로 확인, API/Python 110개 판정 일치 | 합성 fixture·주입 응답 포함. 모든 동작을 실제 Qwen·Google 계정으로 실행한 것은 아니다. |
| 업무 누락 검사 초기 반복 | 실제 Qwen의 한 표 계산→선별→정렬→JSON 생성·저장·실행 성공. B=40, A=30. 그 그래프를 일부러 잘못 바꾼 5가지 대조 사례 모두 저장 차단 | 대조 사례는 Qwen 생성 5회가 아니다. 최종 생성 규격 전체를 입증하지 않는다. |
| 최종 업무 누락 검사 로컬 코드 | Python 1665 통과, 2 건너뜀, subtest 4 통과. 파일 해시도 기록과 일치 확인 | 자동 회귀 검사 수다. 실제 업무 시나리오 성공률이나 ML 평가 수치가 아니다. 통합 후 확인 결과는 동봉 JSON에 별도 기록한다. |

최초 PR27과 계약 수정 시점의 Node 전체 실행에는 S3 보관 실패 처리 검사의 15초 시간 초과가 있었다. 코드 변경 없는 단독 재실행은 통과했지만, 전체 실행을 모두 통과한 것으로 합산하지 않는다. 각 시점의 상세 자료는 아래 문서에 보존한다.

## 3. 미해결 사항

1. **최종 추가 수정본으로 두 표 복합 흐름의 실제 Qwen 생성·저장·실행 확인.** 업무 누락, 결합 조건 오류와 출력 길이 초과를 차단한 실패 기록도 있다. 강제로 성공 처리하지 않았다.
2. **기존 검증기의 파생 열 오판.** 계산 후 생긴 열을 없는 열로 판단하는 사례가 남아 있다. 새 요청 업무 검사는 이 모델의 pass를 신뢰 조건으로 삼지 않는다.
3. **실험용 bounded 생성 방식의 실제 서버 호환성과 안정성.** 서버가 일부 JSON Schema 제약을 무시하거나 거부한 사례가 있었고, 최종 출력 길이 조정 후 확인은 남았다.
4. **배포 환경의 추천 모델 번들·해시·환경 설정과 공개 화면의 전체 동작.** 로컬 격리 저장소 검증과 구분한다.
5. **검수 도구 학습 사례와 라벨 신뢰도, 실제 Google 연결.** 이번 백엔드 수정의 완료 범위가 아니다.

사용자 확인에 따르면 팀장이 공용 RunPod를 중지했다. 그 뒤 Qwen 주소의 HTTP 404가 발생했다. 이를 새 코드 오류로 분류하지 않는다. 신규 저가 GPU 임대는 재고 부족으로 생성되지 않았고, 자동 예약도 만들지 않았다. 기존 팀 Pod는 변경하지 않았다.

## 다음 확인 순서

1. 이 PR에서 기존 실행 오류 수정과 업무 누락 검사 코드를 검토한다. 최종 모델 재검증 전까지 초안 상태로 공유한다.
2. 팀 Qwen이 복구되면 `baseline` 생성 방식으로 기존 한 표·두 표 요청을 다시 실행하고 저장 파일을 대조한다. 모델·설정·커밋을 함께 기록한다.
3. 정상 결과뿐 아니라 일부 업무 누락·잘못된 경계·결합 방향·저장 경로 우회를 차단하는지 확인한다. `bounded`는 별도 실험으로 유지한다.
4. 위 결과를 같은 PR에 추가한 뒤 병합 가능 여부를 검토한다. 운영 배포와 배포 워크플로 수동 실행은 이번 PR 갱신 작업에서 수행하지 않는다.
5. 병합·배포 뒤 실제 화면에서 첨부→생성→확인 저장→실행→다운로드를 확인한다.

코드 검사·타입 검사·기존 그래프 재실행·PR 정리는 GPU 없이 할 수 있다. **실제 Qwen 생성 검증에는 Qwen 서버가 필요하다.** 로컬 서버나 팀 서버가 있으면 신규 RunPod는 필요 없고, 현재처럼 사용 가능한 로컬 모델이 없고 팀 서버도 중지돼 있으면 임시 GPU 서버가 필요하다.
