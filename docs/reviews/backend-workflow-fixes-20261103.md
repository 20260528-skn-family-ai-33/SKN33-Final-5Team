# 복합 워크플로 백엔드 수정과 검증 (2026-11-03)

기준 main: `9cebf9c` (PR #25, #26 병합본). 모델·학습 데이터·배포 설정·Google 연결 코드는 변경하지 않았다.

## 1. 문제가 있던 부분

| 구간 | 재현한 문제 |
| --- | --- |
| 생성 | 기본 도구 설정과 확장 operation의 인자·포트를 섞어 생성했다. 연결된 표를 다시 파싱하거나 앞 노드 이름을 실제 표 값처럼 넣기도 했다. |
| 생성 응답 처리 | JSON 형식이 맞아도 요구사항 설명 길이 등 앱 계약을 어기면 기존 수정 재시도 경로 밖에서 예외가 났다. |
| 파일 선택 | 두 표를 받는 실행을 파일 하나만 허용하는 사전 검사가 막았다. 같은 이름인 서로 다른 원본을 하나의 실행 파일에 연결할 가능성도 있었다. |
| 가공 결과 | 결합 결과처럼 단일 원본 `file_id`가 없는 표를 집계·정렬할 때 필수 키로 읽어 실패했다. |
| 원본 파일 읽기 | 확장 도구의 원본 CSV 읽기를 기본 도구의 '이미 파싱된 표' 조건으로 검사해 실행 전에 차단했다. |
| 하위 워크플로 | 부모가 전달한 문서를 다시 요구했다. 반대로 표를 전달한 경우에는 하위 흐름의 다른 입력 검사까지 생략했다. |
| 업무 결과 | 실제 Qwen 재검증에서 정렬 요청에 불필요한 `is_empty` 필터를 추가했다. 실행 상태는 성공이었지만 결과 파일은 빈 목록이었다. |

## 2. 해결한 내용

- 기본 도구가 읽는 설정 키를 공통 모듈로 관리하고, 축약된 생성 응답은 앱의 전체 설정 형식으로 복원한다.
- 기본 설정과 확장 operation의 생성 규격을 나눈다. Deep Agent는 기본 도구의 대안 operation이 필요하면 `inspect_tool`로 계약을 확인한 뒤 사용한다. 전체 도구 발견 경로와 확장 동작은 유지한다.
- 연결 포트·표 인자·상수/열 비교 조건을 생성 규격에 반영한다. 기존 실행 검증기도 유지한다.
- 설명 길이·근거 ID 오류를 한 번의 생성 수정 경로 안에서 처리한다.
- 실행 전 검사와 실제 읽기가 같은 파일 선택 함수를 사용한다. 서로 다른 원본이 하나의 새 파일에 연결되면 첫 읽기 전에 차단하며, 같은 원본을 명시적으로 재사용하는 경우는 허용한다.
- 단일 원본 ID가 없는 가공 표도 집계·정렬한다. 실제 원본 ID와 검수 표시가 있는 표는 그 정보를 보존한다.
- 원본 파일 operation에는 자체 asset/path 실행 계약을 적용한다. 하위 워크플로에서는 부모가 전달하는 입력 종류만 파일 요구에서 제외하고 다른 입력은 계속 검사한다.
- 정렬만 요청했을 때 `filters=[]`를 쓰고, 결합 키의 null 오류 정책을 빈 행 선택 필터로 바꾸지 않도록 생성 지시를 명시했다. 앞서 발생한 빈 결과 실패도 기록했다.

### 확인한 범위

- Python 전체: **1,569 passed, 2 skipped, 4 subtests passed**. `-1` 라벨 변경·ML 재학습은 하지 않았다.
- `npm run check`: 통과.
- `npm test`: 로컬 접속을 허용한 실행에서 750 통과, 1 건너뜀, 1 시간 초과 취소(15초 제한). 취소된 S3 보관 실패 처리 검사는 코드 변경 없이 단독 재실행해 1건 통과했다. 전체 한 번의 실행이 모두 통과했다고 표현하지 않는다. 첫 제한 환경 실행의 localhost `EACCES` 로그도 보존했다.
- 마지막 생성 지시 보완 후 생성·계약 관련 검사 333건 통과.
- 실제 팀 Qwen `a4b-qwen35-4b-16k:latest`, Deep Agent 경로와 기존 SVM56 후보 힌트를 사용했다. ML 후보가 생성기에 전달되는 trace를 확인했다.
- 기존 합성 CSV로 서비스의 생성·확인 저장·실행 핸들러를 호출했다. 운영 DB·S3·외부 업무 발송은 사용하지 않았다. 수작업으로 그래프를 만들어 대신 실행하지 않았다.
- 최종 한 표 흐름: `qty * 10` 열 계산 → 20 이상 선별 → 숫자 내림차순 → JSON. 실제 결과 B=40, A=30.
- 최종 두 표 흐름: item 기준 left join → `qty * price` → item별 합계 → item 오름차순 → JSON. 실제 결과 A=40, B=10.
- 최종 두 사례 모두 생성·저장·실행 후 실제 저장 파일 내용을 예상 행과 대조했다. 단일 실행 성공을 일반 성공률로 해석하지 않는다.
- CSV는 native 파싱이다. 별도 합성 이미지의 인증된 파서 호출에서 layout `PP-DocLayout_plus-L`, OCR `PP-OCRv5_mobile_det+korean_PP-OCRv5_mobile_rec`, `gpu:0` 사용을 확인했다. CSV 처리에 OCR을 썼다는 뜻은 아니다.

작은 공유용 증거는 같은 폴더의 `backend-workflow-evidence-20261103.json`에 있다. 원시 로컬 로그·실패 응답은 별도 검증 폴더에 보존했다. 인증키·원문 사용자 파일·모델 바이너리는 이 PR에 넣지 않는다.

## 3. 미해결 사항

- 생성 지시 보완만으로 Qwen의 임의 조건 추가가 항상 방지되는 것은 아니다. 복합 요청의 의미 검증·반복 안정성은 추가 확인이 필요하다. 이번 실제 모델 호출은 `A4B_VERIFIER_MODE=defer`였으며 독립 검증기 승인 결과가 아니다.
- 공개 서비스의 HTTP 인증·업로드·확인 저장·실행·다운로드 화면은 배포 뒤 별도로 확인해야 한다. 현재 결과는 최신 main 기반 로컬 서비스 핸들러와 실제 팀 모델의 조합이다.
- Google 연결은 이번 범위에서 제외했다. GPU를 중지·재시작하거나 팀 서버 설정을 바꾸지 않았다.

### PR 반영 후 확인 순서

1. 팀이 PR 변경을 검토하고 병합한다. 현재 main은 병합/푸시 시 EC2 자동 배포가 설정돼 있다.
2. 배포 Actions 성공과 배포 커밋 SHA를 확인한다. 작업 브랜치의 수동 배포도 같은 운영 EC2·데이터를 사용하므로 별도 합의 없이 실행하지 않는다.
3. 공개 서비스에 기존 합성 CSV를 첨부하고 위 두 요청을 생성 → 사용자 확인 → 저장 → 실행 → 다운로드한다.
4. 결과 행·정렬·합계와 실행 로그를 대조하고, 같은 이름 파일 교체·잘못된 파일 종류·하위 워크플로 입력도 확인한다.
5. 생성 의미 오류와 HTTP/배포 오류를 나눠 기록한다. 백엔드가 예외 없이 끝났다는 사실만으로 업무 결과가 맞았다고 판정하지 않는다.
