# 독립 코퍼스 판정 기준

이 35개 요청은 기존 52개와 별도로 작성했다. 모두 독립 검증용 holdout이다. 사례·정답·라벨은 앱 개발이나 모델 선택에 사용하지 않는다. 사전 동결 값은 independent-evaluation-freeze.json에 기록한다. 모호한 두 요청은 cases 밖의 excluded로 남겨 계산에서 제외한다.

## 관찰 단위

각 결과의 사례 ID·원본 사례 해시, 모델 식별자, 단계별 raw/수용 상태, 백엔드 응답의 질문, 최종 route, 검증 상태, 워크플로우와 연결, 합성 실행 행을 확인한다. 합성 metadata는 연결 전제이며 외부 사용 권한을 부여하지 않는다. 질문만 묻고 멈추는 CLARIFY 사례에서 후속 결과를 추정하지 않는다.

- 첫 요청 종료 시 수용된 typed 값이 initial 슬롯 근거다. 원문 반복, 검토·거절된 후보, 일반 draft 기본값은 추출 근거에서 제외한다. 요청한 key/value를 TP로, 누락을 FN으로, 잘못된 확정값을 FP+FN으로 기록한다. 별도 수용된 과잉 값도 근거를 적어 FP로 기록한다. 모델이 null/missing으로 낸 불필요한 슬롯은 값 FP와 구분하고 실제 불필요 질문·상태 오염을 기록한다.
- 질문은 실제 표시 순서, question ID, 필요한 슬롯 및 이미 답한 슬롯을 근거로 판정한다. 한 질문이 두 조건을 명료하게 묻는 경우 둘 다 인정한다. pending이 비어 이전 draft 질문을 집계했다면 이전 질문임을 명시한다. 단어 matcher 실패·오매칭, 미관측 턴과 모델 실패를 구분한다. 재질문율은 실제 후속 질문만 분모로 삼는다.
- 지정된 수정/답변에서 처음 정한 자료, 시각, 시간대, 이전 조건의 보존과 해당 값의 변경을 함께 본다. first와 final을 각각 기록한다. default reference 시각이 바뀌어도 최초 달력 기준을 유지해야 하는 사례는 두 시각을 따로 제공한다.
- 날짜 질의는 사전에 계산한 양 끝 epoch와 현지 zone의 동등성을 확인한다. 동일한 절대 구간을 입증할 수 있으면 표현 차이를 인정한다. 날짜 문자열만 남아 경계 적용 시간대를 검증할 수 없으면 전체 날짜 성공으로 세지 않는다. 자연어 합리성 및 DST 하루의 길이만으로 경계가 정확하다고 판정하지 않는다.
- READY의 업무별 coverage는 실제 수행 가능한 노드 인자·자료·경계값과 입출력 참조·의존 순서가 충족될 때만 인정한다. 같은 도구가 존재하는 것과 업무 충족은 별개 지표다. 한 노드가 둘 이상을 충족하려면 실행 의미와 처리 순서가 같아야 한다. 단일 노드가 비가환 연산의 순서를 바꾸면 인정하지 않는다. 기술적으로 동등한 등록 표현이나 근거 있는 항등 보조 노드는 근거를 기록해 인정한다.
- gold.review_contract.ledger_units를 기준으로 수용 requirement의 업무, typed 값, 미정 조건, 미지원 동작, 의존 관계를 대조한다. 서비스의 실제 조건·capability 관문에서 먼저 막히면 그 다음 장부가 없음을 기록한다. planner가 원문에서 업무를 복원했더라도 장부 추출을 완전하다고 기록하지 않는다. 같은 산출물의 재진술·동일 산출물의 중복 장부·실제 서로 다른 산출물을 구분한다. 과잉 업무, 누락, 모순, 근거 없는 확정, source 누락을 라벨과 증거에 남긴다. 장부 도달 사례에서의 정확도와 전체 사례 중 장부 도달률의 분모를 함께 표시한다.
- whole_request_success는 기대 route와 전체 의도를 함께 평가한다. READY는 모든 업무, 인자, 시간, 변경·의존성 및 전달 대상이 맞고 근거 없는 작업이 없어야 한다. CLARIFY는 모든 필수 질문을 실제로 묻고 지정한 값을 유지해야 한다. UNSUPPORTED는 실제 카탈로그/고정 전달 계약의 제한을 지적하고 지원되는 일부를 전체 완료로 안내하지 않아야 한다. 장부의 미지원·출처 근거 및 사용자에게 드러난 상태를 별도로 기록한다.
- 독립 다운로드 링크 둘을 명시한 요청은 고정 기준의 runner/공개 다운로드 API가 마지막 하나만 제공하는 제약을 적용한다. 내부 outputs가 둘이거나 서로 다른 형식이 등록돼 있다는 사실만으로 두 파일 전달을 입증하지 못한다. 반면 단일 파일과 이메일 전송을 함께 요청한 경우 서로 다른 사용자 결과다. 개별 채널·자료 출처·본문 바인딩을 확인한다. 단일 산출물의 재진술을 두 파일로 늘려서도 안 된다.
- local_synthetic는 안전한 native read_table/filter_sort/aggregate_table/calculate_columns/write_result/finish 조합만 실행하여 전체 행과 순서를 고정 oracle에 대조한다. 등록된 동등 operation을 사용해 READY여도 실행 allowlist에서 제외될 수 있다. 이때 설계 성공과 실행 미측정을 나누고 실행 대상 전체, 실제 실행 수, 성공 수를 각각 보고한다. 외부 메일, 계정, DB, 문서 모델 재실행은 별도 실행하지 않는다.
- 결과는 기존 52개·독립 35개, 모델 호출·코드 전용, before/after, 미실행·실패를 별도 집계한다. 후보별 schema 통과, 독립 사람 평가, 토큰 총액 등 측정되지 않은 항목은 미측정으로 남긴다. 분모가 0이면 미정으로 보고한다.

## 실행 호환성

프로젝트 루트에서 기존 Node 실행기의 --corpus에 이 디렉터리의 independent-evaluation-cases.json을, --corpus-profile에 runpod-rebuild를, --expected-gold-sha에 freeze 파일의 canonical gold_sha256을 전달한다. 실행 프로필/모델·endpoint·비밀·응답 예산은 평가 주관자가 별도로 확인한 값으로 자식 프로세스에 주입한다. 새로운 수정 후 측정은 이 gold와 환경에 대응하는 전체 baseline을 지정한다. adjudicator에는 동일 --corpus를 명시한다. 기존 52개 전용 최소 범주 수 및 고정 adjudicator 경로만 지원하는 구 버전은 이 파일을 처리할 수 없다.

검증 담당자는 결과에 맞춰 gold를 고치지 않는다. 정답이 모호하거나 실제 카탈로그/시간대 계약과 충돌하는 새 증거가 나오면 원문과 원래 판정을 보존하고 영향 ID·분모를 별도 이견으로 표시한다.
