# RunPod custom Qwen 평가 판정 규칙

이 규칙은 baseline 추론 전에 고정한다. 기존 52개와 독립 코퍼스는 각각 같은 gold의 전후 측정을 비교한다. 독립 코퍼스의 모든 사례를 holdout으로 배정할 수 있다. 사례의 카테고리별 최소 수는 기존 코퍼스의 구성에만 해당한다. 두 코퍼스의 비율은 각각 보고한다.

## 입력과 검토 단위

각 라벨은 평가 결과의 `source_case_sha256`에 연결한다. `model_calls`는 원본 응답을, `stages[].parsed_state`는 노드가 반환한 상태 변경을 제공한다. 장부 경계의 `ledger_before`는 노드 입력, `ledger_after`는 입력에 반환값을 적용한 관측값이다. 사용자가 실제로 받은 상태는 `turns[].response`로 확인한다. `turn_attempts`에는 제출 후 worker 예외로 응답이 남지 않은 턴도 포함한다. 각 단계의 `model_call_indices`는 실행 전체 기준이며 사례의 `model_call_offset`을 빼면 사례 내부 배열 인덱스가 된다.

후보와 수용값은 **해당 단계에서** 의미를 비교한다. 최종 planner가 빠진 작업을 복구해도 그 전 단계의 장부 누락은 남는다. 모델 리뷰의 `faithful`은 관측 항목이며 정답 판정은 원문·고정 gold·실제 설정과 연결을 대조한다. 원문 재인용, 일반 설명, 아직 선택하지 않은 기본 템플릿 값은 typed 슬롯 추출로 채점하지 않는다.

## 장부 지표

| 지표 | 분자 | 분모 |
|---|---|---|
| 후보의 소유값 충돌률 | 기존 소유 장부의 확정값 또는 명시적으로 미정인 상태와 모순되는 모델 후보 주장 수 | 비교할 소유 상태가 있고 후보가 그 키를 실제로 주장한 기회 수 |
| 수용된 소유값 충돌률 | 같은 소유 상태와 모순되는 값이 해당 단계 후 실제 유효 장부에 남은 기회 수 | 위 기회 중 단계 후 유효값을 확인할 수 있는 기회 수 |
| 충돌 후보의 수용률 | 충돌 후보 값이 그대로 수용된 기회 수 | 원문·소유 장부와 충돌한 후보 중 수용 결과를 판정할 수 있는 기회 수 |
| 후보 중복 업무율 | 하나의 requirements 응답 안에서 이미 표현된 같은 업무의 두 번째 이후 항목 수 | 파싱해 검토한 requirements 후보의 업무 항목 수 |
| 수용 장부 중복 업무율 | 하나의 수용된 requirement 장부 안에서 같은 업무의 두 번째 이후 항목 수 | 실제 새로 반환된 requirement 장부의 검토한 업무 항목 수 |
| 수용 장부 필수 업무 누락률 | 최종 수용 장부에서 빠진 고정 업무 수 | 최종 READY가 정답이며 requirement 장부에 도달한 사례의 고정 업무 수 |
| 종단 필수 업무 미표현율 | 수용 장부에서 빠진 업무와 장부 미도달 업무의 합 | 최종 READY가 정답인 검토 사례의 모든 고정 업무 수 |

소유값 비교의 단위는 사례·사용자 턴·응답 후보·소유 장부 키다. 같은 후보의 같은 키는 한 번만 센다. 최신 사용자 답변이 소유값을 합법적으로 바꾼 시점에는 변경 후의 소유값을 사용한다. 이전 단계의 값이 그대로 남아 비교 가능하면 그 값으로 수용 충돌을 판정한다. 후보가 파싱되지 않았거나 단계 결과의 근거가 없으면 누락 사유와 수를 기록한다. `null`은 미검토 또는 미확인이고 0은 검토한 결과의 0이다. 실제 호출과 반환 역시 분리한다.

업무 동등성은 동작·출처·인자·대상·결과와 의존성을 비교한다. 같은 사용자 요구에 조건 답변을 적용했거나 같은 내용을 다시 적어 새 작업이 되었다면 중복이다. 서로 다른 대상, 분기, 단계 입력이나 결과를 요구하면 별도 업무다. 재시도한 모델 응답은 각각 후보 모집단으로 보되, 이전 장부가 후속 노드의 입력으로 다시 보인 횟수는 수용 장부 수에 더하지 않는다. `gold.workflow.tasks[].id`를 고정 업무 단위로 쓰고, 독립 코퍼스의 의미 경계는 `gold.review_contract`와 함께 검토한다. 결정되지 않은 조건 때문에 정상적으로 CLARIFY하는 사례는 최종 READY 업무 누락 분모에서 제외한다. 도달한 장부가 새로 중복된 업무를 생성했고 원래 의무도 누락했다면 두 지표에 각각 반영한다.

## 질문과 세션

기존 scorer 질문 분모는 각 응답의 `pending_questions`가 있으면 이를, 비어 있으면 `draft.questions`를 사용한다. 별도로 두 출처의 개수, 응답 상태, 사례 및 질문 ID를 기록한다. `needs_clarification`이 아닌 응답이 빈 pending과 이전 질문 텍스트를 draft에 보존한 경우 stale draft 재노출로 센다. backend 필드 관측과 실제 브라우저 노출은 구분한다. 이미 답한 조건을 다시 물었는지는 질문 텍스트·이전 실제 답변·해결된 상태를 함께 검토한다. 아직 답하지 않은 필요한 질문이 다시 표시된 경우는 해결된 질문의 반복률에 넣지 않는다.

`turn_attempts`의 제출·worker 오류, `turns`의 저장 응답, 같은 session/thread, 이력 접두부 보존, revision 증가, 직전 pending과 제출된 question ID 일치를 각각 센다. READY 이후 수정에는 질문 ID가 없으므로 질문 ID 분모에서 제외한다. 고정 변경 슬롯 전체 수, 실제 후속 응답이 저장된 변경 슬롯 수, 미관측 기회를 모두 보고한다. 타당한 질문이 고정 답변 어휘와 매칭되지 않은 경우를 시스템이 불필요한 질문을 한 경우와 나눠 기록한다.

## 집계 범위

기존 intent, slot, routing별 F1, 질문, 답변 반영, validation, task coverage 및 실제 허용된 합성 실행은 기존 scorer와 동일한 분모를 유지한다. 전체 성공에는 기대 route, 기준에 맞는 질문·답변, 필수 업무와 인자·연결·기존 조건 보존을 모두 요구한다. 실행이 지정된 사례는 기대 실행 결과도 확인한다. 입력 행·순서·출력에 영향을 주지 않는 항등 노드는 별도 기록한다. 원문에 없는 효과나 외부 동작을 추가한 workflow는 전체 실패다. 주 실패 원인은 최초로 확인된 원인이 발생한 단계에 한 번 배정하고 최종 차단 단계도 기록한다. 주 측정과 반복 측정의 각 사례를 그대로 보존한다.

HTTP 전송 시도, HTTP 응답 수, 선택 모델의 관측된 반환 응답, 실패, 미완료, probe를 구분한다. SDK 원문은 SDK가 조립한 응답이며 개별 스트림 프레임과 구분한다. 이 수치만으로 서버의 총 추론 수·토큰 청구·비용을 추정하지 않는다.
