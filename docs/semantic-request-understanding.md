# 표현에 독립적인 요청 해석

같은 뜻의 문장을 서비스·동작·수량·기간·필터·예약·추가 업무로 먼저 해석하고, 실제 도구 설정으로 변환한다. `내 Gmail`, 어순, 존댓말마다 완성 문장 예외를 추가하지 않는다. 기존 정확한 요청 레시피는 모델 호출을 생략하는 최적화로 유지하지만, 다른 표현을 거부하는 기준으로 사용하지 않는다.

## 처리 구조

1. `attachment_gate`가 현재 사용자 턴의 시간 맥락을 저장한다.
2. `request_meaning.py`가 원문 전체를 `RequestMeaning`으로 추출한다. 수량·상대 날짜에는 실제 근거 발화와 원문 표현이 필요하다.
3. 별도의 새 검토 대화에서 원문과 후보를 비교한다. 필터·추가 작업·부정·후속 변경의 누락이나 추가를 검사한다. 검토는 같은 모델을 사용하는 추가 호출이며, 의미의 정확성을 수학적으로 보장하지 않는다.
4. 원문·자료·시간 맥락의 fingerprint와 후보 digest에 검토 결과를 연결한다. 누락되거나 오래된 검토, 변경된 후보는 재사용하지 않는다.
5. 서비스 어댑터가 검토된 구조를 등록 도구의 인자로 변환한다. 모델이 임의의 Gmail 검색문을 실행 인자로 직접 지정하지 않는다.
6. 기존 지원 판단, 요구사항/실행 설정 검증, 사용자 검토와 저장 승인을 계속 거친다. 이 단계에서 Gmail 조회나 요약 실행은 하지 않는다.

일반 의미 추출은 성공 시 추출 1회와 검토 1회로 총 2회 호출한다. 계약 오류나 검토 거부가 있으면 한 번 더 추출·검토하여 최대 4회로 제한한다. 끝까지 실패하거나 모델 연결이 실패하면 후보를 폐기하고 전체 원문을 일반 설계기로 넘긴다. 이 경우 일반 설계기의 후속 호출은 별도다. 기존 정확한 레시피는 의미 추출 추가 호출이 없다.

## 현재 어댑터 범위

공통 의미 구조를 사용하는 첫 어댑터는 Gmail이다. 현재 소스 별칭은 `gmail`과 `지메일`이다. 다른 서비스와 아직 등록하지 않은 별칭은 기존 일반 설계 경로를 사용한다.

- Gmail 한 작업의 읽기와 일반 요약, 최신 N건(1~500건), 오늘·어제 기간, 안 읽은 메일 조건을 지원한다. 지원되는 기간과 안 읽음 조건은 함께 보존한다.
- 기간이나 안 읽음 조건이 있고 개수를 정하지 않은 경우 최대 100건이라는 한도를 설명한다. 명시적인 “모든 메일” 요구를 이 한도로 바꾸어 처리하지 않는다.
- 기존 예약 규격에 맞는 전날 조회 또는 안 읽은 메일 반복 조회를 지원한다. 기존 레시피와 저장된 일정의 변경 규칙도 유지한다.
- 오래된 순서, 임의 날짜 범위, 발신자·제목 등 다른 필터, 특정 요약 관점, 첨부파일, 파일 저장·전송·삭제·번역, 여러 독립 작업은 축소하지 않고 일반 설계기로 보낸다. 지원 여부는 그 경로의 실제 도구 계약으로 판단한다.

`gmail_summary.py`와 요구사항 검증은 같은 의미 구조에서 만든 수량·조회 조건·본문 연결·요약 지침을 비교한다. 표현이 같아야 통과하는 전체 문장 정규식을 의미 검증의 필수조건으로 삼지 않는다. 화면 설명은 등록 도구와 실제 초안 설정을 사용하며, 모델의 내부 분석 설명을 그대로 노출하지 않는다. 초안 설명은 실행 완료 알림이 아니다.

## 시간 맥락

`temporal_context.py`는 UTC 기준시각과 IANA 시간대를 사용한다. 시간대 우선순위는 다음과 같다.

1. 상태에 명시된 `user_timezone`
2. 서버 설정 `A4B_DEFAULT_TIMEZONE`
3. 기존 앱 기본값인 `Asia/Seoul`

서버 운영체제의 로컬 시간대는 추측하지 않는다. 명시된 시간대가 비어 있거나 잘못됐다면 알 수 없는 상태로 남기며, 기본값으로 조용히 바꾸지 않는다. Windows 환경에는 프로젝트 requirements에 있는 `tzdata`가 필요하다.

같은 턴의 검증 재시도와 checkpoint 재시작은 같은 기준시각을 사용한다. 각 사용자 발화의 시간 맥락도 보존하므로 다음날 “5개만 해줘”라고 답해도 최초 요청의 “어제” 날짜가 이동하지 않는다. 이전 기록에 수신시각이 없다면 임의의 과거 시각을 만들어 넣지 않는다. 날짜 경계는 해당 시간대의 자정으로 계산하므로 서머타임 전환일을 무조건 24시간으로 취급하지 않는다.

단발 요청의 “어제”는 해당 발화의 절대 조회 구간으로 고정한다. 반복 예약의 “전날”은 매 실행일을 기준으로 계산한다. 날짜 해석의 기본 시간대가 있다고 사용자가 정하지 않은 예약 주기나 실행 시각을 자동으로 정하지 않는다.

## 검증

백엔드 개발 환경을 활성화한 뒤 다음 계약·그래프 테스트를 실행한다.

```sh
cd Backend
python -m pytest tests/design/test_request_meaning.py tests/design/test_meaning_graph.py tests/design/test_temporal_context.py tests/design/test_public_draft_summary.py tests/capabilities/test_gmail_summary.py tests/capabilities/test_gmail_schedule_design.py tests/capabilities/test_gmail_hourly_unread_design.py -q
```

이 테스트들은 모델 응답 fixture를 주입한다. 같은 의미의 표현이 같은 workflow로 연결되는지, 수량·필터·추가 작업이 보존되는지, 검토 거부가 자동 완료로 이어지지 않는지, 날짜 경계·후속 변경·checkpoint·승인·저장이 올바른지를 검사한다. **테스트 통과는 실제 모델이 모든 표현을 정확히 추출한다는 뜻이 아니다.**

실제 모델 검증은 저장소 루트의 합성 코퍼스 실행기로 별도 수행한다. 아래 모델 이름과 주소는 검증하려는 서버에 실제 등록된 값으로 지정한다.

```sh
python scripts/verify/verify-request-meaning-live.py --base-url http://127.0.0.1:11434 --model qwen3.5:9b --case recent5_screenshot --case yesterday_screenshot --timeout 600 --output data/request-meaning-9b-smoke.json
```

`--case`를 생략하면 전체 코퍼스를 실행한다. 실행기는 `.env`나 계정 자료를 읽지 않고 합성 요청만 사용하며, 메일 조회·워크플로우 실행도 하지 않는다. 모델별 비교에는 같은 코퍼스, 프롬프트, 생성 설정을 사용한다. 결과 JSON의 실제 응답 모델명, 코드·프롬프트·스키마 hash, 검토 결과, 호출 수와 시간, `completed_corpus`를 함께 확인한다. 연결 실패·시간 초과·자원 부족으로 중단된 실행을 해석 정확도나 전체 통과로 보고하지 않는다.

로컬 9B 추론은 메모리와 응답 시간이 크게 필요할 수 있다. 사용자 작업에 영향을 줄 때는 로컬 추론을 중단하고, 여유가 있는 명시된 모델 서버에서 작은 사례부터 별도로 검증한다. 이 문서는 실제 모델 평가의 성공을 선언하지 않는다.

## 모델 변경과 배포

운영 설정 예시에 있는 `a4b-qwen35-9b-final664-pilot32k`와 `a4b-qwen35-9b-previous-pilot32k`는 인계된 파인튜닝 모델 이름이다. 공식 로컬 `qwen3.5:9b`와 동일한 모델로 간주하지 않는다. 모델 목록에 이름이 있는 것, 앱 기본 모델 설정, 기존 대화의 모델 별칭 전환, 실제 추론에 사용된 가중치는 구분해야 한다. 운영 프로필과 전환 규칙은 [배포 문서](a4b-automatic-deployment.md)를 따른다.

더 좋은 모델은 추출 품질을 개선할 수 있지만, 전체 문장 정규식 거부·누락된 날짜 맥락·고정 응답 문구 같은 코드 문제는 모델 이름 변경만으로 사라지지 않는다. 실제 운영 모델의 품질은 해당 가중치와 설정으로 별도 측정한다.

이 변경은 로컬 소스 수정이다. 운영에 적용하려면 해당 소스를 배포하고 실제 서비스의 새 대화·후속 변경·기존 대화 저장 경로를 확인해야 한다. 코드 수정이나 로컬 테스트만으로 운영 배포 또는 운영 9B 검증이 완료된 것은 아니다.
